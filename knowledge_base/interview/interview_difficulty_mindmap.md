# 项目难点回答思维导图大纲

> 结构：背景 - 难点 - 方案 - 收益。适合导入幕布 / XMind / 飞书脑图后展开复习。

## 中心主题：复杂直播业务的难点拆解与解决方案

### 1. 开播链路架构

- 背景
  - 开播不是单点按钮，而是预览、开播中、关播三阶段链路
  - 涉及相机、推流、美颜、贴纸、礼物、连麦、小游戏、公屏等多业务
- 难点
  - 多阶段状态流转复杂
  - 多业务资源同时接入，容易形成巨石页面
  - 相机、推流、组件生命周期容易错位
- 方案
  - `BroadcastCoreController` 做编排中枢
  - 生命周期 `Task` 管前后台、销毁、阶段切换
  - Tetris `Element` 管 UI 组件挂载
  - setting 灰度控制新能力
- 收益
  - 流程、生命周期、UI 展示解耦
  - 新业务可插拔接入
  - 核心链路更稳定，线上可快速回滚

### 2. 短触框架

- 背景
  - 短触承载电商、任务、游戏、红包等即时玩法入口
  - 来源包括 API、WRDS 消息、JSB
- 难点
  - 多来源同时到达，容易并发更新 UI
  - add / delete / activate / 临态 / 增强短触状态交织
  - 入场动画、排序、优先级容易互相打断
- 方案
  - 三来源统一成一套短触模型
  - 用串行任务队列处理状态变更
  - 临态用保护期、超时回退、优先级比较
  - 增强短触用 `priority + dynamicPriority` 做唯一性选举
- 收益
  - 多业务入口低成本接入
  - 动画顺序稳定
  - 状态一致、体验统一
  - 可降级、可运营

### 3. Hybrid 容器化基础

- 背景
  - 直播大量活动、营收玩法由 Lynx / H5 动态下发
  - 前端页面需要直播通参、房间上下文、生命周期事件和 JSB 能力
- 难点
  - JSB 各自取上下文会导致耦合和串房
  - Hybrid 异步加载、容器复用、切房会导致通参不准
  - 生命周期监听容易泄漏
- 方案
  - `WebcastBizContainer` 作为直播专属容器入口
  - 五大 Service 收口 schema、UA、globalProps、lynxConfig、webScheme
  - 容器层统一注入 `LiveContext` 到 `extraContainerContext`
  - `LiveGlobalPropsService` 用 `LiveContext` 二次校正 `room_id / anchor_id`
  - 销毁时统一清理监听和 stateStore
- 收益
  - 前端页面像原生一样消费房间能力
  - 通参和宿主口径一致
  - JSB 边界更清晰
  - 降低串房、泄漏、错误事件投递风险

### 4. KMP 跨端

- 背景
  - 直播互动功能过去 Android / HarmonyOS / iOS 多端重复实现
  - KMP 的目标是让多端消费同一份业务逻辑和状态
- 难点
  - 判断哪些逻辑适合下沉，哪些必须留平台侧
  - Room / User 等大对象跨端同步成本高
  - 多端模型、消息、埋点口径容易漂移
- 方案
  - 业务逻辑下沉到 `commonMain`
  - 两种消费模式
    - 逻辑共享：KMP 输出 State / Action，各端原生 UI 渲染
    - Compose 共享 UI：KMP 写 `@Composable`，各端用平台容器承载
  - Android 用 `AndroidView` / `ComposeView` 接入原生 View 或 Compose UI
  - HarmonyOS 用 `ArkUIViewTopLayer` / `ArkUIComponentContent` 承载 ArkTS 创建的内容
  - UI、动画、播放器、系统能力走平台分叉
  - 消息用 `rawPayload / Protobuf` 保持双端解码一致
  - 数据同步按访问模式选择对象复制或代理共享
  - sourceSet 隔离抖音专属和 SaaS 空实现
- 收益
  - 一份业务逻辑，多端消费
  - 可选择原生渲染，也可复用 KMP Compose 组件
  - 降低重复开发和多端漂移
  - 消息字段不丢、埋点口径一致
  - 多产物构建边界更安全

### 5. 小窗 / 画中画

- 背景
  - 用户离开直播间后仍希望连续观看
  - 需要覆盖站内小窗、系统画中画、后台播放、实况窗
- 难点
  - 直播生命周期、播放器生命周期、页面生命周期、系统前后台不一致
  - 容易出现多播放器、声音异常、画面暂停、回房间状态错乱
  - 监听和播放器资源容易泄漏
- 方案
  - 拆清站内小窗、站外画中画、后台播放状态
  - 播放器显式 `pause / resume / stop / release`
  - 回直播间时统一收敛全屏页和小窗状态
  - 多实例和监听器跟随生命周期清理
- 性能优化细节
  - 播放器资源复用与释放
    - 小窗态尽量复用当前直播流上下文，避免频繁重新建播放器
    - 退房、回房、切后台时显式释放无用播放器实例，防止多实例并存
  - 音视频降级
    - 后台或弱展示场景支持 video 降级 audio，减少解码、渲染和功耗压力
    - 小窗不可见或被系统收起时，避免继续高成本渲染
  - 生命周期降噪
    - 前后台、页面切换、小窗展开/收起只处理状态真正变化的事件
    - 避免重复触发 pause / resume / enter / exit 导致播放器抖动
  - 监听清理
    - 小窗 listener、房间 listener、播放器回调跟随生命周期注销
    - 重点防止「回直播间后旧 listener 还在」导致重复回调和内存泄漏
  - UI 更新控制
    - 小窗态只保留必要 UI 状态，减少全量组件刷新
    - 封面、静音状态、播放状态做最小粒度更新
- 收益
  - 连续观看体验更完整
  - 降低播放器状态错乱和内存泄漏
  - 支撑多种小窗形态稳定运行
  - 降低后台播放和小窗场景的解码、渲染、内存与功耗压力

### 6. 直播回放容器

- 背景
  - 鸿蒙直播需要补齐回放设置、实时回放、付费回放、高光、分享链路
  - 涉及前端容器、JSB、本地 KV、开播参数、房间权限
- 难点
  - 前端设置、端侧缓存、开播参数、服务端房间状态容易不一致
  - 付费回放和普通回放口径不同
  - 开播前、直播中、关播后状态链路长
- 方案
  - 打通「入口 → 容器 → JSB → 本地状态 → 开播参数 → 房间状态」
  - JSB 接入 `getReplaySetting / updateReplaySetting / syncReplayStatus`
  - 本地 Repo 保存关键状态
  - 开播参数补齐 `gen_replay`
  - 付费场景由门票信息覆盖普通设置
- 性能优化细节
  - 容器按需加载
    - 回放设置、高光、分享等页面只在入口触发时拉起 Hybrid 容器
    - 避免开播页初始化阶段提前加载重型前端页面
  - 状态本地化
    - 回放开关、自动发布等状态落到本地 Repo / KV
    - 开播参数构造时直接读本地状态，减少重复请求和前端依赖
  - JSB 状态同步收口
    - `getReplaySetting / updateReplaySetting / syncReplayStatus` 收口读写路径
    - 避免多个入口各自维护状态，减少不必要的状态广播和重复写入
  - 参数构造前置
    - 开播前把 `gen_replay` 等参数一次性拼入 create 参数
    - 避免开播中再补状态导致链路等待或二次请求
  - 付费场景优先级
    - 付费回放由门票信息覆盖普通设置
    - 避免前端和端侧反复纠偏，减少状态冲突
  - 容器释放
    - 回放设置页、分享 H5、高光页退出时清理容器和监听
    - 防止前端容器长驻导致内存增长
- 收益
  - 回放链路端到端一致
  - 支撑普通回放、实时回放、付费回放、高光和分享
  - 前端配置能稳定进入开播参数
  - 减少开播页初始化压力、重复请求和 Hybrid 容器常驻内存

### 7. 开播 Toolbar

- 背景
  - 主播开播前 / 开播中功能入口多
  - 美颜、贴纸、连麦、管理、分享等入口需要灵活编排
- 难点
  - 如果每个按钮写死在页面，会产生大量 if/else
  - 外显 Toolbar 和更多面板之间需要互转、replace、过滤
  - 不同房间类型和开播形态下展示规则不同
- 方案
  - 抽象按钮能力
  - 外显 Toolbar 和更多面板统一编排
  - 支持按钮 replace、互转、过滤
  - 业务通过配置接入
- 收益
  - 主播入口从页面逻辑中解耦
  - 新按钮接入成本更低
  - 多业务入口编排更灵活

### 8. 为什么不用更简单的方案

- 背景
  - 很多需求短期可以直接在页面加逻辑
  - JSB 可以直接取全局状态
  - 消息也可以直接转 JSON
- 难点
  - 简单方案短期快，长期扩展成本高
  - 上下文容易错
  - 生命周期清理不统一
  - 多端口径容易漂移
- 方案
  - 先拆边界，再做实现
  - 短触用统一模型和队列
  - Hybrid 用容器层注入上下文
  - KMP 用 `commonMain` 下沉业务逻辑
- 收益
  - 后续扩展更稳定
  - 问题边界更清晰
  - 业务能力可复用，而不是一次性需求代码

### 9. 我具体解决了哪些问题

- 背景
  - 项目覆盖业务入口、动态容器、跨端复用、生命周期治理
- 难点
  - 问题不是单类，而是状态、上下文、稳定性三类交织
- 方案
  - 状态一致性
    - 短触多来源并发
    - 小窗多生命周期
    - 回放前端设置与开播参数一致
  - 上下文和边界
    - Hybrid `LiveContext` 注入
    - KMP 平台能力分叉
    - sourceSet 隔离
  - 稳定性
    - 监听释放
    - 容器销毁
    - 播放器 release
    - 组件复用状态污染治理
- 收益
  - 不只是做 UI 或接接口
  - 把复杂链路收敛成可维护框架
  - 降低后续业务接入和排障成本

### 10. 最大的技术判断

- 背景
  - 复杂业务经常容易被拆成一个个功能点堆代码
- 难点
  - 如果不识别变化维度，抽象会错
  - 抽象过轻会导致重复，抽象过重会拖慢落地
- 方案
  - 先判断变化维度
    - 短触：来源、优先级、动画、状态
    - Hybrid：容器、通参、JSB、生命周期
    - KMP：业务逻辑、平台能力、数据同步
    - 小窗：直播、页面、播放器、系统生命周期
  - 再决定抽象边界
  - 通过状态机、队列、容器注入、commonMain、生命周期清理分别解决
- 收益
  - 方案不是一次性需求
  - 后续业务能复用
  - 技术表达能从「做了什么」升级到「为什么这么做」

## 总结主干

- 背景
  - 我做的项目大多不是单点功能，而是直播复杂链路
- 难点
  - 多阶段、多来源、多上下文、多端、多生命周期
- 方案
  - 状态机解决阶段流转
  - 队列解决并发顺序
  - 容器注入解决上下文
  - `commonMain` 解决跨端复用
  - 生命周期清理解决稳定性
- 收益
  - 复杂链路可维护
  - 业务能力可复用
  - 稳定性边界更清晰
  - 体现复杂链路拆解能力和平台化抽象能力
