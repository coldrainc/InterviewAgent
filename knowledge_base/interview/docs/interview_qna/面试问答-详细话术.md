## 1. 全链路诊断是怎么做的？（Workflow Agent 平台）

### 主回答话术

我在 Workflow Agent 平台里负责的是全链路诊断和问题排查这一块。这个平台是面向研发场景的 AI Agent 任务执行平台，一个任务跑起来涉及很多环节——模型推理、工具调用、Sandbox 里执行代码，任何一环出问题都可能导致整个任务失败，而且失败现象往往只是"结果不对"或者"卡住"，很难一眼看出是哪里的问题。

我的做法是建一套三级 ID 串联的链路追踪体系：
- **traceId** 对应一整条 Workflow，贯穿任务从启动到结束；
- **spanId** 对应单个推理步骤或工具调用，记录这个步骤的输入、输出、耗时、状态；
- **agentRunId** 对应单次 Agent 运行实例，用来区分同一个 Workflow 的多次重试或并发执行。

这三个 ID 把推理过程、工具调用、Sandbox 状态全部关联起来，形成一个完整的执行链路视图。

在证据采集上，我做了一个 **Runtime Trace + Workflow 阶段账本**。每个阶段都会把输入输出和状态记下来作为确定性证据——不是靠日志去拼凑，而是有结构化的阶段账本，出了问题可以直接回放某个阶段。

排查异常时，我会定位到具体的 span：是模型推理的问题（比如幻觉、拒绝回答），还是工具执行失败（参数错误、超时），还是 Sandbox 状态异常（配置残留、TOML 损坏）。定位到根因之后，再给出修复建议，比如重试、改写 Prompt、回滚配置。

这块工作的价值在于，Agent 执行链路本来是个黑盒，有了全链路诊断，问题从"不知道哪坏了"变成"能定位到具体 span 并给修复方向"，保障了 Agent 执行的稳定运行。

### 预判追问

- **Sandbox 配置残留导致 TOML 损坏是什么场景？**
  多轮会话里，前一轮的 Sandbox 配置没清干净，新一轮加载时和残留配置冲突，TOML 解析失败。我用了 SHA-256 校验 + 原子替换 + 失败回滚来保证配置一致性——配置变更先算摘要，写临时文件再 rename，失败自动回滚到上一版本。

- **怎么保证诊断本身不拖慢执行？**
  Trace 是异步采集的，不阻塞主执行链路；阶段账本写的是增量快照，不是全量 dump。

- **诊断数据存哪？怎么查？**
  存 MongoDB，按 traceId 建索引，前端有链路视图可以按 traceId 查整条链路、展开 span 级别。

## 2. 为什么选 KMP？跨语言通信性能怎么优化？

### 主回答话术

选 KMP 主要是结合我们直播业务场景来定的。直播场景里，播放器、小窗、直播卡片这些强依赖原生能力，不太可能用一套自绘 UI 把三端都覆盖了，Flutter 那种自绘方案在跟系统组件、鸿蒙特性结合时成本很高。

KMP 的思路是**业务逻辑层共享、UI 层各端原生**。网络层、数据模型、业务策略、工具类这些纯逻辑我们用 Kotlin 写一次，三端共用；UI 层鸿蒙用 ArkUI、iOS 用 SwiftUI、安卓用 Compose。这样既复用了核心逻辑，又保留了原生体验，对直播这种重原生的场景最合适。

我们最终把代码复用率做到了 70%+，三端功能能同步上线，业务迁移成本降低了一半以上。

跨语言通信性能这块，Kotlin 和 ArkTS/JS/原生之间通信是有开销的，高频调用会很明显。我的优化思路是三方面：
- **减少跨语言调用次数**：把多次小调用合并成一次批量传输，比如列表数据一次性传过去而不是逐条。
- **数据结构优化**：用 ByteArray 或 Protobuf 代替 JSON 序列化，减少序列化反序列化的开销。
- **异步化**：耗时逻辑放在 Kotlin 侧协程里跑，通过回调或 Flow 返回结果，不阻塞 UI 线程。

这几个优化下来，数据传输效率提升了 30%+。

### 预判追问

- **KMP 和 RN 在你这个场景下怎么取舍？**
  RN 用 JS 写 UI，跨三端时鸿蒙端适配成本高，而且直播播放器/小窗这些原生能力 RN 要写原生模块桥接，三端各桥一遍。KMP 逻辑共享、UI 原生，鸿蒙直接用 ArkUI，跟系统结合更顺。

- **70% 的复用率是怎么算的？**
  按共享模块代码行数占总业务逻辑代码的比例算，UI 层不算在内。

- **Banner 业务迁移 KMP 的过程？**
  把 Banner 的数据协议和轮播策略抽成 KMP 模块，各端只实现 UI 渲染和曝光埋点；迁移后验证数据一致性、埋点对齐、性能基线对齐。

## 3. H5/Lynx Hybrid 混合架构是怎么落地的？

### 主回答话术

鸿蒙端从 0 到 1 建设，纯原生开发成本太高、迭代慢，但纯 H5 性能又不够——首屏慢、交互流畅度差，直播这种实时性要求高的场景撑不住。

我们选了 H5/Lynx 混合架构。Lynx 是类 RN 的高性能动态化框架，核心播放和交互用它来做，保证性能；活动页、运营位这些用 H5，灵活可动态下发。两者通过一个容器来桥接。

容器的职责是几块：路由分发（决定某个页面走 H5 还是 Lynx）、预加载（提前预热容器和资源）、生命周期管理（页面切换时容器的复用和回收）、JS Bridge 通信（H5/Lynx 和原生之间互调）、降级（某个方案不可用时回退）。

这套架构落地后，业务迁移成本降低了 50%+，同时兼顾了性能和动态化能力——核心交互流畅，运营活动能随时下发。

### 预判追问

- **Lynx 和 RN 有什么区别？**
  Lynx 是字节自研的高性能动态化框架，思路和 RN 类似但渲染层用自绘，性能更可控，和字节内部基建结合更好。

- **H5 和 Lynx 之间怎么通信？**
  通过容器提供的 JS Bridge，H5 调原生能力、原生通知 H5 都是走 Bridge。

- **降级策略是什么？**
  Lynx 加载失败或超时降级到 H5，H5 再失败降级到兜底页。

## 4. RAG 双路召回是什么？Query Rewrite 解决什么问题？

### 主回答话术

双路召回是向量检索 + 关键词召回并行跑，再融合重排。

单用向量检索的问题是：业务里有大量专有名词、ID、缩写，向量检索语义相近能召回，但精确匹配弱——比如查某个开播配置项的具体名字，向量可能召回一堆语义相近的，但用户要的那个反而排不到前面。

单用关键词召回（BM25 或 ES）则相反：精确匹配强，但语义泛化弱，用户口语化提问就召不回。

所以我做了双路：向量检索走一路召回 TopK，关键词召回走另一路 TopK，两路结果用 RRF 或者 cross-encoder 重排，融合出最终结果。这样语义和精确匹配都能兼顾。

Query Rewrite 解决的是用户提问不规范的问题。用户问"开播挂了"，但知识库里的文档写的是"开播失败"或"开播崩溃"，直接检索召回不好。改写层会把口语化提问改写成检索友好的查询——补全实体、拆解多意图，再配合业务同义词词典把"开播挂了"映射成"开播失败/崩溃"，召回率就上来了。

这套机制下来，Agent 业务类问题的准确率明显提升，幻觉率显著改善，重复性业务问询也明显降低。

### 预判追问

- **重排用 RRF 还是 cross-encoder？怎么选？**
  RRF 简单快，纯靠排序融合；cross-encoder 准但慢，需要算 query-doc 相关性。看量级选，量小用 cross-encoder 提精度，量大用 RRF 保延迟。

- **同义词词典怎么维护？**
  业务方提，定期评审入库；也可以从历史 query 里挖掘高频同义表达。

- **知识库怎么和 Agent 结合？**
  把知识库检索封装成标准 MCP Skill，注册到 Workflow Agent 平台，Agent 需要业务事实时主动调用检索，检索结果作为事实证据注入 Prompt，约束模型只基于知识回答，并标注引用来源。

- **知识入库流水线？**
  对接 Confluence、飞书文档、工单、代码注释四类数据源，统一清洗、切分（按标题/语义/长度）、打标签（业务域、文档类型）、Embedding 入库，向量库和关键词索引双写；基于文档版本/时间戳做增量同步。

## 5. RN 拆包和 H5 打包优化怎么做？构建效率提升 40%+ 靠什么？

### 主回答话术

**RN 拆包**的背景是单 Bundle 体积大、首屏慢，而且多业务模块耦合在一起，一个业务发版会阻塞其他业务。我的做法是按业务模块拆分 JS Bundle——主包放公共逻辑和首页，业务子包按模块拆，原生侧做一个 Bundle 管理器，按路由预加载或懒加载子包。用的是 Metro 多入口打包。拆完之后首屏提速、业务能独立发版、回归风险也降低了。

**H5 打包优化**主要靠几招组合：
- **缓存**：用 Webpack 5 的持久化缓存（filesystem cache），二次构建只重算变更部分。
- **并行**：thread-loader 多线程编译，Terser 多进程压缩。
- **按需**：Tree Shaking、动态 import、splitChunks 分包，去掉没用到的代码。
- **体积**：依赖分析排查重依赖和体积大的包，该替换的替换。

这套下来构建效率提升 40%+。这个我在赤兔元框架的整体工程改造里落地，框架支持 RN 和 Web 双端，统一了工程化规范。

### 预判追问

- **Metro 多入口打包怎么配？**
  配多个 entry，每个业务模块一个入口，输出独立 Bundle；公共依赖可以抽 shared module。

- **RN 子包预加载策略？**
  按路由——用户即将进入某业务时预加载该子包；冷启动只加载主包，首页可交互后再预加载高频子包。

- **Webpack 持久化缓存的失效场景？**
  配置变更、依赖版本变更、loader/plugin 升级会失效；通过 contenthash 控制，构建产物用文件名 hash 做缓存。

- **构建优化怎么量化？**
  构建前后的耗时对比，CI 上埋点采集，取多次构建的均值对比。

## 6. LiveView 在鸿蒙直播中怎么接入？踩过什么坑？

### 主回答话术

LiveView 是鸿蒙提供的直播渲染组件，支持视频流在系统层面的高效渲染和悬浮显示，是鸿蒙端直播的核心能力。

接入的核心是处理好 LiveView 和 ArkUI 页面生命周期的协同。Surface 的创建和复用时机很关键——页面切换、App 切后台切前台、路由跳转时，Surface 的回收和重建都要精确控制，回收早了画面会闪，重建晚了会黑屏。

我们接入 LiveView 后，又接了实况窗、直播卡片、小窗这些鸿蒙特色能力，让直播在桌面、负一屏、悬浮窗等场景都能展示，这是鸿蒙端区别于其他端的差异化体验。

这块我作为核心开发从 0 到 1 搭建，性能提升 40%+，业务迁移成本降低 50%+。

### 预判追问

- **Surface 复用的具体策略？**
  按播放场景维护 Surface 池，同屏多个播放场景复用同一 Surface，切换时通过状态机管理 ownership 转移，避免反复创建销毁。

- **切后台直播怎么处理？**
  切后台走小窗/后台播流策略，Surface 降级到小窗渲染，保持音频连续；回前台再接管全屏 Surface。

- **ArkUI V1 和 V2 状态管理有什么坑？**
  V1 的 @Observed 对嵌套对象不响应，深层属性修改不触发更新；V2 用 @ObservedV2/@Trace 改进了。列表渲染的 key 管理也容易出问题，复用错位常见。

## 7. Workflow Agent 三层架构怎么设计？ReAct 和其他模式区别？

### 主回答话术

三层是 Web、Runtime、Sandbox。

Web 层负责会话管理、UI 编排、Workflow 定义和资产配置，是用户交互入口。Runtime 层是 Codex Runtime，Agent 执行引擎，跑 ReAct 循环、调度工具、管理上下文，独立进程隔离模型推理和业务服务。Sandbox 层是工具执行和代码运行的隔离环境，保证安全和可重复。

分层的好处很明确：一是隔离，模型执行和业务服务解耦，模型挂了不影响业务；二是 Sandbox 隔离避免工具执行污染主进程，代码执行出错能 reset；三是便于独立扩缩容和故障隔离。

执行模式上我们用 ReAct——模型输出思考过程、调用工具、观察结果、再思考，循环执行。它和 Function Calling、Plan-and-Execute 的区别是：Function Calling 是单轮调用工具，缺乏多步规划能力；Plan-and-Execute 是先规划完整计划再执行，刚性强、中途纠错难；ReAct 边想边做，灵活纠错，更适合研发场景的长链路任务，比如"改个 bug、跑测试、看结果、再改"这种循环。

### 预判追问

- **为什么不用纯 Function Calling？**
  研发任务是多步的，需要观察中间结果再决定下一步，单轮 Function Calling 表达不了这种循环。

- **Runtime 为什么独立进程？**
  隔离模型执行和业务服务，避免模型进程崩溃带崩业务服务；也便于 Runtime 独立升级和扩缩容。

- **Sandbox 隔离用什么实现？**
  容器化隔离，配置同步走 SHA-256 校验 + 原子替换 + 回滚，保证 Sandbox 状态一致性。

## 8. MCP 扩展体系和动态工具注册怎么设计？

### 主回答话术

MCP（Model Context Protocol）是标准化的模型和工具/资源的协议，让 Agent 能力可插拔。我们的设计目标是让业务方能自助给 Agent 加新能力，不用走发版。

核心几块：动态工具注册——运行时注册 Skill，不需要重启服务；资产解析和版本锁定——每个 Skill 的资产（配置、代码）有版本，保证可追溯可回滚；Sandbox 物化——Skill 执行需要的依赖和环境物化到 Sandbox；MCP 初始化——按注册的 Skill 初始化 MCP server。

价值是 Agent 能力按需扩展，业务方接入新工具就像装插件一样，平台可扩展性大幅提升。

### 预判追问

- **动态注册怎么保证安全？**
  Skill 注册走审核和沙箱化执行，权限按需授予，敏感操作走审批。

- **版本锁定怎么用？**
  每个 Skill 带 version，Workflow 执行时锁定使用的 version，保证可复现；升级走灰度。

## 9. 上下文管理怎么做？长对话 Token 超限怎么办？

### 主回答话术

上下文管理是 Agent 的核心难点，Token 超限是常态。我的策略是几方面：

滑动窗口 + 摘要压缩。保留最近 N 轮原文，更早的压缩成摘要再注入上下文，这样既保住近期细节，又控制总量。

工具结果裁剪。工具返回的长输出——命令日志、大段代码——先截断或摘要再进上下文，原始结果存到外部存储，需要时再取。

关键状态持久化。Turn 级状态存库，支持会话恢复和回放，不靠上下文里塞所有历史。

这样长对话也能稳定跑下去，不会因为 Token 超限崩。

### 预判追问

- **摘要会不会丢信息？**
  会，所以摘要只压非关键历史，关键决策和错误信息保留原文；也可以按需从外部存储捞回原文。

- **会话恢复怎么实现？**
  Turn 级状态存库，恢复时从最近 Turn 重建上下文，不重放整个历史。

## 10. 知识入库流水线和增量更新怎么做？

### 主回答话术

入库流水线对接四类数据源：Confluence、飞书文档、工单、代码注释。

流程是拉取 → 清洗（去噪去重）→ 切分（按标题/语义/长度）→ 打标签（业务域、文档类型）→ Embedding → 入库。入库时双写——向量库和关键词索引都写，支撑双路召回。

增量更新基于文档版本和时间戳，只同步变更的部分，不全量重灌。

### 预判追问

- **切分策略怎么定？**
  优先按文档结构（标题层级）切，结构不明显的按语义 + 长度切，避免切断语义。

- **代码注释怎么入库？**
  按函数/类粒度抽注释，打标业务域，作为代码知识辅助研发排障。

- **打错标签怎么纠？**
  有评测集定期跑，召回准确率不达标的文档回头人工校验标签。

## 11. RN→Web 兼容怎么处理？token 模块化怎么做？

### 主回答话术

RN→Web 兼容我们用 react-native-web 做适配层。难点在样式差异——RN 默认 Flex 方向是 column，Web 是 row；单位 RN 用无单位，Web 要 px；API 差异像 Animated、Platform 这些要做条件分支。

token 模块化是把设计 token——颜色、间距、字号——统一管理，多端主题切换靠 token 切换。这样同一套组件在 RN 和 Web 上视觉一致，换主题只改 token 不动组件代码。

这块在海豚组件平台一期落地的，研发成本降低 25%+。

### 预判追问

- **react-native-web 有什么坑？**
  第三方依赖不全兼容，有些原生模块要自己 polyfill；样式计算性能在大列表场景要注意。

- **token 怎么多端分发？**
  token 定义一份，按平台生成对应格式（RN 的对象、Web 的 CSS 变量），构建时注入。

## 12. 开播框架是什么？福袋热点怎么带来业务增长？

### 主回答话术

开播全链路是从推流鉴权到房间创建、观众分发的完整链路。我负责的开播框架是把开播流程抽象成可配置的状态机——推流鉴权、美颜滤镜、场景配置、推流、房间创建，每步可配置，业务方按场景拼装，不用每改一次就动核心代码。

- **福袋防刷怎么做？**
  风控规则 + 频率限制 + 异常行为识别，高并发下用幂等和限流保护。

## 13. 海外直播多语言怎么做？

### 主回答话术

## 14. 直播端 Agent 上下文建设与测评怎么做？

### 主回答话术

直播端 Agent 的上下文建设是几块：系统 Prompt 定义 Agent 角色和边界；业务知识注入——把直播业务规则、SOP 注入上下文，约束模型回答范围；历史会话管理，保住多轮上下文；工具能力注册，让 Agent 能调业务接口。

测评是构造业务场景测试集，评估三个维度：准确率（回答对不对）、幻觉率（编不编）、工具调用正确率（调对没调对）。根据测评结果迭代 Prompt 和检索策略，持续优化。

这块和知识库结合紧密——知识库作为事实知识来源约束模型，减少业务类幻觉。

### 预判追问

- **测评集怎么构造？**
  从真实业务问询里抽高频场景，人工标注标准答案；区分业务事实类和流程类。

- **幻觉率怎么测？**
  人工评审 + 规则校验，对业务事实类问题检查回答是否在知识库有据可查，无据还断言即算幻觉。

## 15. 讲一个 Agent 执行链路异常排查案例（故事题）

### 参考讲述结构

按 STAR 讲：背景（场景）→ 任务（要解决的问题）→ 行动（怎么排查）→ 结果（根因和修复）。

**可用素材**：
- **现象**：某个研发 Workflow 跑到中间工具调用步骤失败，任务卡住，结果不对。
- **排查**：用 traceId 查整条链路，定位到失败的 spanId，看 span 输入输出。发现是工具调用超时，进一步看 Sandbox 状态——前一轮配置残留导致新一轮加载的 TOML 损坏，Sandbox 启动异常，工具执行环境不对。
- **根因**：多轮会话配置同步有竞态，旧配置没清干净。
- **修复**：引入 SHA-256 校验 + 原子替换 + 失败回滚，保证配置一致性；加了阶段账本对账，状态不一致提前发现。
- **预防**：加配置一致性门禁，CI 跑 Sandbox 配置同步用例。

### 预判追问

- **怎么发现是配置残留而不是工具本身的问题？**
  span 输出显示工具超时，但工具参数对；查 Sandbox 状态账本发现环境加载异常，再追到 TOML 解析失败，才定位到配置残留。

## 16. RAG 准确率不达标时怎么调优？（故事题）

### 参考讲述结构

**可用素材**：
- **现象**：某类业务问询召回不准，Agent 回答错或者答不出。
- **排查**：先看是召回环节还是生成环节。查检索召回结果，发现目标文档根本没进 TopK，问题在召回。
- **分析**：该类问询是口语化 + 专有名词混用，纯向量召回语义偏了，纯关键词召回又召不到口语化提问。
- **调优**：上双路召回（向量 + 关键词），加 Query Rewrite 把口语改写成检索友好的查询，上业务同义词词典映射黑话，重排层用 cross-encoder 提精度。
- **验证**：用测评集回归，该类问询准确率从不及格提到合格线以上。
- **持续**：把错例沉淀成负样本，定期回归。

### 预判追问

- **怎么判断是召回问题还是生成问题？**
  看召回结果里有没有正确文档——有正确文档但生成错了是生成问题，没有正确文档是召回问题。

- **cross-encoder 和双塔怎么取舍？**
  cross-encoder 准但慢，适合重排阶段小规模精排；双塔快但粗，适合召回阶段大规模初筛。我们召回用双塔，重排用 cross-encoder。

## 20. 讲一个鸿蒙端上线遇到的风险/故障（故事题）

### 参考讲述结构

**可用素材**：
- **现象**：某个直播场景在鸿蒙端上线后，特定操作路径下 LiveView 画面丢失或黑屏，iOS/安卓不复现。
- **排查**：抓不到现场，靠日志和埋点还原操作链路；发现是切后台再回前台时，Surface 被 ArkUI 页面生命周期提前回收，但 LiveView 还持有引用，重建时机错位。

- **预防**：加了生命周期对齐的集成测试，覆盖切后台/回前台/快速切换等边界场景。

### 预判追问

- **为什么只在鸿蒙复现？**
  鸿蒙 ArkUI 生命周期和 iOS/安卓不同，Surface 回收策略不同；其他端的生命周期和 LiveView 对应关系不一样。

- **怎么快速止血？**
  热修复先延迟回收策略上线止血，再根治做状态机。

## 21. KMP 迁移中遇到的最难问题（故事题）

### 参考讲述结构

**可用素材**：
- **现象**：Banner 业务迁移 KMP 后，鸿蒙端偶现数据延迟/丢更新，安卓/iOS 正常。
- **排查**：Kotlin 侧数据没问题，跨语言到 ArkTS 时丢失；发现是 Kotlin 协程异步回调和 ArkUI 状态更新时机不对，回调到 ArkTS 时 UI 已经卸载或状态已变。
- **根因**：跨语言异步回调的生命周期管理缺失，回调没有和组件生命周期绑定。
- **修复**：回调加生命周期守卫，组件卸载时取消回调；协程用 Job 绑定组件生命周期，统一销毁。
- **成果**：跨语言通信稳定性提升，数据传输效率提升 30%+。

### 预判追问

- **为什么安卓/iOS 没问题？**
  Compose/SwiftUI 的状态系统和 Kotlin 协程集成更原生；鸿蒙 ArkTS 和 Kotlin 互操作是 expect/actual 桥接，异步回调路径不同。

- **跨语言通信怎么避免类似问题？**
  所有跨语言异步调用都绑定消费方生命周期，提供统一的 cancel 机制；不允许"裸回调"。

## 22. 技术选型你怎么做决策？（综合方法论题）

### 话术

我的选型方法论是四步：

第一，**先明确约束**——业务场景、团队栈、性能要求、人力、时间。脱离约束谈选型都是耍流氓。

第二，**列候选 + 对比维度**。比如 KMP vs Flutter vs RN，对比维度是原生体验一致性、鸿蒙适配成本、复用率、团队学习成本、生态。

第三，**做小范围验证**。选型不靠拍脑袋，搞个 POC 跑核心场景——KMP 选型时我先迁移 Banner 一个业务验证数据一致性和性能基线，再扩大。

第四，**看长期成本**。不只是能不能跑起来，要看维护成本、升级成本、招人成本。有些方案快但后期坑大。

最后决策要能讲清楚"为什么是它，为什么不是其他"，并留退路——选型错了怎么降级。

### 预判追问

- **KMP 选型时 Flutter 怎么被淘汰的？**
  直播重原生，Flutter 自绘 UI 和系统组件/鸿蒙特性割裂，适配成本高；KMP UI 原生更顺。

- **选型错了怎么办？**
  设计上保留降级路径——Hybrid 架构里 H5 和 Lynx 互为降级；KMP 模块和原生保留接口，必要时回退原生。

## 23. 原理深度追问

### 向量检索索引（HNSW / IVF）

- **HNSW**：层次化小世界图，查询时从顶层入口逐层向下贪心搜索，精度高、查询快，但内存占用大、构建慢。适合对召回质量要求高的场景。
- **IVF**：倒排文件，先聚类分桶，查询只扫近邻桶，速度快、内存省，但精度受桶数影响。适合大规模初筛。
- **取舍**：百万级文档用 HNSW 保精度；千万级以上用 IVF 省资源，必要时 IVF + HNSW 混合（IVF 分桶 + 桶内 HNSW）。

### Embedding 模型怎么选

- 中文场景选中文友好的模型（如 M3E、BGE 中文版）；多语言用 multilingual 模型。
- 维度：768/1024 平衡效果和存储/检索成本，超大批量可降维。
- 评测：用业务 query-doc 对跑召回指标（Recall@K），不要只看公开榜单。

### React Native 新架构（JSI / Fabric / TurboModule）

- **JSI**：JS 和原生直接持引用调用，不走 Bridge 序列化，延迟低、支持同步调用。
- **Fabric**：新渲染器，C++ 层渲染，替代旧 UIManager，性能更可控。
- **TurboModule**：原生模块懒加载，按需实例化，不启动全量注册。
- **价值**：解决旧 Bridge 的异步瓶颈和大列表性能问题。我们 RN 拆包和性能优化也受益于新架构。

### Webpack 构建原理 / Tapable

- Webpack 核心是依赖图 + Tapable 事件系统。从 entry 出发递归建依赖图，每个模块过 loader 转译，插件通过 Tapable 钩子介入编译各阶段。
- 优化点：持久化缓存（5 的 filesystem cache）、并行（thread-loader）、按需（Tree Shaking 依赖 ES Module 静态分析）。

### Docker 容器隔离原理

- 靠 Linux Namespace 隔离视图（PID/网络/挂载/UTS），Cgroup 限制资源（CPU/内存/IO），联合文件系统分层镜像。
- 比 VM 轻——共享宿主内核，不虚拟整套 OS。Sandbox 隔离用容器化，保证工具执行环境干净可 reset。

### Node.js 事件循环

- 基于 libuv，分阶段：timers → pending callbacks → idle/prepare → poll → check → close callbacks。
- 微任务（Promise）在每个阶段间清空；nextTick 优先级高于 Promise。
- 注意：CPU 密集会阻塞事件循环，要走 worker_threads 或子进程。

## 24. 软技能 / 协作类
