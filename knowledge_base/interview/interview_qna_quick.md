# 面试 Q&A 口语速记版

> 地铁上快速过一遍用。每题记住一句主结论，再记 2-3 个关键词就够。

## 0. 开播整体架构怎么讲？

**Q：开播链路你怎么讲清楚？**

**A：**

我会先说，开播不是一个按钮，而是一条复杂链路。它有预览、开播中、关播三个阶段，还牵涉相机、推流、美颜、贴纸、礼物、连麦、小游戏、公屏这些能力。

所以我把它拆成三层：

- 第一层是编排中枢，`BroadcastCoreController` 管状态机和几个子控制器。
- 第二层是生命周期 Task，负责页面出现、隐藏、前后台、销毁这些时机要做的事。
- 第三层是 Tetris Element，负责 Toolbar、公屏、礼物、连麦这些 UI 能力挂在哪里、什么时候挂载。

一句话就是：开播不是堆功能，而是把多阶段、多业务、多资源收敛成一套可编排、可插拔、可回滚的框架。

**记忆点：** 中枢管状态，Task 管生命周期，Element 管 UI。

---

## 0.1 Task 和 Element 怎么区分？

**Q：开播里的 Task 和 Element 区别是什么？**

**A：**

Task 管「什么时候做事」，Element 管「展示什么东西」。

比如前后台、页面销毁、开播阶段切换，这种跟生命周期有关的逻辑，放 Task。

比如 Toolbar、公屏、礼物盘、连麦坑位，这种 UI 组件，放 Element。

这两层拆开之后，业务接入就不会都塞进一个大组件里，后面扩展也更清楚。

**记忆点：** Task 管流程，Element 管展示。

---

## 0.2 开播怎么保证状态和资源稳定？

**Q：开播涉及相机、推流、贴纸、连麦，怎么保证不乱？**

**A：**

我会从三点讲。

第一，用状态机控制流程，比如预览、开播中、关播，每一步都要做权限、重复启动、媒体房这些校验。

第二，用生命周期 Task 统一清理，页面隐藏、前后台、销毁这些时机都统一分发，避免监听和资源漏掉。

第三，新能力都走 setting 灰度，线上出问题可以快速关掉。

另外开播页有些场景主动关组件复用，是为了避免复用外层 context 后状态污染，主播链路稳定性优先。

**记忆点：** 状态机控流程，Task 控清理，setting 控风险。

## 1. 短触为什么要有任务队列？

**Q：短触直接更新列表不行吗？为什么要搞队列？**

**A：**

不太行。短触来源太多了，有接口、有 WRDS 消息、还有 JSB，可能同一时间都在加图标、删图标、激活图标。

如果直接并发改列表，很容易出现几个问题：顺序乱、动画互相打断、临态或者增强短触状态被覆盖。

所以我这里用队列把这些操作串起来，一个个处理。这样入场动画、状态更新、列表渲染都是稳定的。

**记忆点：** 多来源并发 → 队列串行化 → 动画和状态稳定。

---

## 2. 临态和增强短触有什么区别？

**Q：临态和增强短触怎么区分？**

**A：**

临态可以理解成普通短触的临时强化，比如短时间放大、前置、加宽，展示完会回到普通状态。

增强短触更像一个强运营入口，它会从候选里选一个优先级最高的出来展示，而且同一时间只能有一个。它的优先级比临态更高，可以压制或者打断临态。

**一句话：** 临态是临时强化普通入口；增强短触是全局唯一强入口。

---

## 3. 为什么要统一 API / 消息 / JSB 三种来源？

**Q：三种来源差异挺大的，为什么要统一？**

**A：**

因为来源不同，但后面的处理其实一样：都要校验权限、过滤配置、排序、展示动画、处理临态、埋点、最后卸载。

如果每个来源各写一套，后面策略会重复，而且体验很容易不一致。

所以我把三种来源统一成同一套短触数据结构，都走同一条流水线。这样后续新增业务，只要按统一协议接入就行。

**记忆点：** 来源不同，处理相同；统一模型，统一流水线。

---

## 4. Hybrid 为什么在容器层注入 LiveContext？

**Q：为什么不让每个 JSB 自己去拿 LiveContext？**

**A：**

因为 JSB 自己拿上下文，很容易变成各拿各的，全局依赖很重，还可能出现串房。

容器最清楚当前页面属于哪个直播间，所以我在容器 `onShow` 的时候统一把 `LiveContext` 注入到 `extraContainerContext`。后面所有 JSB 都从这个上下文里取房间能力，比如消息管理器。

这样边界更清楚，也方便容器销毁时一起释放监听，减少泄漏和串房风险。

**记忆点：** 容器统一注入；JSB 不碰全局；避免串房和泄漏。

---

## 5. Hybrid 通参为什么还要二次校正？

**Q：已经有通参了，为什么还要用 LiveContext 校正 room_id / anchor_id？**

**A：**

因为 Hybrid 页面有异步加载、容器复用、切房这些情况。通参生成的时间点，不一定就是容器最终绑定的房间。

`LiveContext` 才是当前容器真实绑定的房间上下文。所以我会用它再校正一次 `room_id`、`anchor_id`、`sec_anchor_id`。

这样可以避免前端请求串房，也避免埋点归因错。

**记忆点：** 异步/复用/切房 → 通参可能旧 → LiveContext 做最终校正。

## 6. KMP 哪些该下沉，哪些不该下沉？

**Q：KMP 里什么放 commonMain，什么留平台侧？**

**A：**

我的原则是：业务逻辑下沉，平台能力分叉。

适合下沉的是 ViewModel、状态机、数据模型、消息解析、埋点口径、配置读取这些逻辑。它们和平台关系不大，而且多端必须一致。

不适合下沉的是 UI 细节、复杂动画、播放器、系统能力、生命周期细节。这些东西每个平台差异很大，强行下沉反而会影响体验和稳定性。

**记忆点：** 逻辑下沉，UI 和系统能力分叉。

## 7. KMP 为什么用 rawPayload / Protobuf，不用 JSON？

**Q：消息桥接为什么传 Protobuf bytes，不直接转 JSON？**

**A：**

因为直播消息源头本来就是 Protobuf。直接传 raw bytes，Android 和 HarmonyOS 都从同一份 bytes 解码，口径最一致。

如果中间转 JSON，可能会丢字段，特殊类型也容易出问题，还多了一次转换成本。

当然 raw bytes 不好调试，所以我补了 `raw_payload_base64` 的 mock 通道，方便本地构造消息验证。

**记忆点：** 不丢字段、口径一致、少转换；调试靠 base64 mock。

## 8. KMP 的 iOS 到底落地了吗？

**Q：你说一键三端，iOS 真的上线了吗？**

**A：**

没有，这个我会说清楚。现在实际落地的是 Android 和 HarmonyOS，iOS 是架构预留，还没有业务接入上线。

我说一键三端，更多是讲长期架构目标：一份 commonMain 逻辑，Android/HarmonyOS 已经验证，iOS 在模型映射、FFI 数据同步、渲染分叉上做预留。

所以对外我会说：两端已落地，iOS 预留，不会包装成 iOS 已经上线。

**记忆点：** Android + HarmonyOS 已落地；iOS 预留，未上线。

## 9. 小窗最难的生命周期问题是什么？

**Q：小窗/画中画最难的点在哪里？**

**A：**

最难的是几个生命周期不一致：直播生命周期、播放器生命周期、页面生命周期，还有系统前后台。

用户可能退后台、打开别的页面、从小窗回直播间、切全屏、切音视频流。任何一步没处理好，就会出现画面停住、声音异常、多个播放器同时存在、回房间状态不一致，甚至泄漏。

我的处理思路是先把状态机分清楚：站内小窗、站外画中画、后台播放。然后播放器的 pause、resume、stop、release 都显式做，回直播间时再统一收敛状态。

**记忆点：** 多生命周期不一致；状态机拆清楚；播放器显式释放。

## 10. 回放容器怎么保证状态一致？

**Q：回放里前端状态、本地 KV、开播参数怎么对齐？**

**A：**

我把这条链路串成一条线：入口 → 容器 → JSB → 本地状态 → 开播参数 → 房间状态。

前端通过 `live.getReplaySetting` 读状态，通过 `live.updateReplaySetting` 改状态。端上把关键状态写进本地 Repo，比如是否生成回放、是否自动发布。

开播的时候，再从本地状态里读出来，写到 `gen_replay` 这些开播参数里。付费直播特殊一点，要用门票里的回放配置覆盖普通设置，保证付费回放口径正确。

**记忆点：** JSB 写本地，本地进开播参数，付费场景特殊覆盖。

## 最后总括

如果最后让你总结，可以这么说：

> 我做这些项目，本质上是在把直播里的复杂业务从零散功能收敛成可复用框架。短触解决多来源入口调度，Hybrid 解决前端页面拿直播上下文和能力，KMP 解决跨端逻辑复用，小窗和回放解决复杂生命周期和状态一致性。我的优势是能拆复杂链路、做平台化抽象，也比较关注生命周期和稳定性边界。
