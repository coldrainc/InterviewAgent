# Workflow Agent & Harness 技术方案调研 + 选型决策 + 面试讲述

> **目标**：针对抖音直播内部"研发场景 AI Agent 工作流"（任务看板 / 工作流编排 / 会话管理 / MCP Skill 扩展 / Sandbox 隔离 / 全链路诊断 + RAG 知识库），系统调研业界现有方案，给出选型决策与落地路线。
> **定位**：不是写代码，是做**技术方案（面试能讲清楚"为什么选/不选 A、为什么这么做、trade-off 是什么"）**。

## 一、业界方案全景调研（8 大主流，按定位分 4 类）

### 1.2 ① 自治 Code Agent 平台（SWE 定位）

#### 方案 A：OpenHands（原名 OpenDevin，AllHands-AI / 原社区合并入新 Org）

| 维度 | 细节 | 信息来源验证 |
|---|---|---|
| **定位** | "Open-source autonomous software-engineering agent" | Stars 77,254（2026-06）、Forks 9,814[^ghtrends]；另有 67k 统计[^raw-metadata] |
| **架构** | EventStream 事件驱动 + **Docker 一线 sandbox** + Python SDK + REST/WS + Web UI + CLI + VSCode 集成 + MCP 工具 | SDK 技术报告 arXiv 2511.03690[^openhands-sdk] |
| **核心能力** | Sandbox（bash/file_edits/browser_use/jupyter）· Event memory condenser · MCP client · 多模型 · 任务规划 · Security analysis | managed-agents-landscape 对比表[^codeagents-landscape] |
| **Benchmark** | **SWE-bench Verified 77.6%（Opus 4.5）/ 66%（Sonnet 4.5）**，开源 scaffold 最高；DeepSeek V3.2 51% | codesota 对比[^codesota-oh]、raw-metadata[^raw-metadata] |
| **部署** | Docker Compose / K8s Helm；Cloud 版含 Slack/Jira/Linear 集成、多用户、RBAC；Enterprise 自托管（Source-Available 许可，>1 月要买 License） | ghtrends[^ghtrends]、raw-metadata[^raw-metadata] |
| **多租户** | ❌（设计上单租户）| codeagents-landscape[^codeagents-landscape] |
| **学习曲线** | 重（Docker + 完整 UI 运行时） | ghtrends Setup weight: heavy[^ghtrends] |
| **企业级生产就绪度** | ⭐⭐⭐⭐ Code Agent 路径最成熟开源项目；但多租户/审计不足 | codesota Verdict: "Production path"[^codesota-oh] |

**优势**：
- 开源 Code Agent 里 **Sandbox 最强**（Docker 一线隔离 + browser tool 做 GUI 自动化），这和我们 Workflow Agent 的 Sandbox 需求高度重合
- SWE-bench 分数开源 scaffold 最高，EventStream + Condenser 内存管理方案是业界标准参考，可直接借鉴
- 社区极活跃（日提交，30+ 贡献者），迭代速度快

**劣势**：
- **多租户弱**，单用户单 password 设计；对于公司级接入（多团队/权限）是硬伤
- **定位偏 Code Agent（编程任务）**，对我们"全栈工作流 + RAG 知识库 + 诊断分析"这种非纯代码的 Agent 场景，工具层需大幅二开
- Enterprise 功能是 Source-Available 许可，用超过 1 个月要买 License，合规要确认

**生产案例**：无公开大厂内部生产案例（多数是自建 PoC）。Cloud 版宣称 NCR / VMware / Ancestry / Choice Hotels 等用（但这些是 Harness.io CD 用户，注意不要混淆，下面会区分两个"Harness"）。

#### 方案 B：SWE-agent（普林斯顿 NLP，学术基线）

| 维度 | 细节 | 验证 |
|---|---|---|
| **定位** | "Agent-Computer Interface (ACI) 学术基线" | NeurIPS 2024，Stars 14k+[^codesota-oh] |
| **架构** | 极简 Agent-Computer Interface：ls / find_file / open / scroll / edit(linear line-range replace) / submit —— 文本接口为 LLM 优化，无复杂 SDK | codesota Architecture 侧图[^codesota-oh] |
| **Benchmark** | Opus 4.5 72.0%（低于 OpenHands 的 77.6%）；Sonnet 4.5 61.2%；DeepSeek 46% | codesota 对比表[^codesota-oh] |
| **内存** | 把 Full trajectory 全塞进 context（没有 Condenser，省复杂度但耗 token） | codesota |

**结论**：**只适合做研究 baseline / 写论文参考 ACI 设计思想，不适合直接生产落地**。OpenHands 是"production path"，SWE-agent 是"research path"[^codesota-oh]。我们可以借鉴它的 linear edit（你 Workflow Agent 的 code_edit 工具设计可以参考），但不要选它作为主框架。

### 1.3 ② 通用 Agent 编排框架（和我们 Workflow Agent 定位最接近）

#### 方案 C：LangGraph（LangChain 出品）

| 维度 | 细节 | 验证 |
|---|---|---|
| **定位** | "Graph-based state machine for stateful multi-agent AI systems" | v1.0 GA 2025-10；LangSmith SOC2/ISO27001/2022 + HIPAA（商业 Hosted）[^similarlabs-compare] |
| **Stars 2026-06** | 36.1k（略低于 CrewAI 54.6k/AutoGen 59.4k，但 Stars ≠ 健康度：AutoGen 已 maintenance）| similarlabs June 2026 真实计数[^similarlabs-compare] |
| **架构** | 有向状态图（StateGraph）：Node = LLM/tool/分支决策，Edge = 状态转移；内置 Checkpointer（MemorySaver/SQLite/Postgres/MongoSaver）· LangSmith 追踪回放 · Human-in-the-loop 原生一等公民 · Subgraph 嵌套 · 并行分支 | Techseria 企业级生产对比 8 维度打分：Checkpointing/HITL/Audit Trail/Observability 全满 5/5[^techseria-enterprise] |
| **生产客户** | Klarna（support agent）、Uber（自动代码迁移 + 用例生成）、LinkedIn（招聘/SQL Bot）、Replit（coding copilot）、Elastic（威胁检测）、AppFolio（10+ 小时/周节省 × 2× 准确率）| similarlabs-compare 中引用[^similarlabs-compare] |
| **学习曲线** | 陡（2–3 周上手），首 Agent 3-5 天 | marsdevs 对比表[^marsdevs-compare] |
| **可控性** | **所有框架最高**——图拓扑、状态 schema 全显式；每步状态可 replay（LangSmith UI 直接从失败步骤回放）。Techseria 报告"在金融合规流水线中，把 Debug 从半天降到 < 30 分钟"[^techseria-enterprise] |
| **确定性** | 高——你把流程控制从 LLM 收到服务端代码，LLM 只做单步，不和框架抢编排 | Experience 1596661 Success 1 关键结论也验证这点 |
| **可观测性** | LangSmith 业界最佳：每步输入输出、Token、Latency、Trace 全链路、Annotation 数据集 |

**优势**（为什么多次方案里默认用它）：
- **和我们自研 Runtime 的"三层架构"思路高度兼容**：Web（LangSmith UI 替代自研 + API Expose）、Runtime（LangGraph 图 + Checkpoint 替代/增强自研 ReAct）、Sandbox（OpenHands 的 Docker sandbox 可以单独复用作为 LangGraph Tool 执行层，不冲突）
- **状态持久化 = 故障恢复基础**：Agent 跑到 step 6 挂了，Checkpoint 直接从 step 5 重播；这对我们"全链路诊断"做故障回放很有价值
- **审计痕迹结构化**：每个 state transition 都有 Checkpoint，不是日志事后补——对企业合规非常友好
- **多 Agent 协作支持一流**：Subgraph 可以把"诊断 Agent / RAG 检索 Agent / 代码修复 Agent / 报告生成 Agent"各自做成 Graph 再嵌套，团队协作开发方便

**劣势**：
- **上手贵**：团队要先理解 StateGraph、Memory、Checkpointer 三个概念才能写对复杂流程（2-3 周学习曲线）
- **没有内置 Sandbox**：sandbox 自己接（推荐复用 OpenHands 的 Docker sandbox 层作为 Tool）
- **LangSmith 商业版收费**：如果要自托管可观测性，可以接我们自己写的 OTel + Elastic + Grafana，不依赖 LangSmith 商业

#### 方案 D：CrewAI

| 维度 | 细节 | 验证 |
|---|---|---|
| **定位** | "Role-based autonomous agent teams" | 融资 \$18M Insight Partners 2024-10；自称 "450M+ agentic workflows / 月" + "Fortune 500 ~60%"（未审计）[^similarlabs-compare] |
| **Stars** | 54.6k（2026-06，高于 LangGraph 36.1k）[^similarlabs-compare] |
| **架构两层**：**Crews**（自治多 Agent 团队：角色 Role/Goal/Backstory + 顺序/分层进程）+ **Flows**（事件驱动确定性 pipeline：@start/@listen 装饰器 + 条件/并行路径 + UUID 每 run）| similarlabs-compare |
| **学习曲线** | **最缓**——1-2 天出首 Agent，角色 + 目标 + 背景 YAML 定义完就跑 | marsdevs 1-2 days[^marsdevs-compare] |
| **确定性** | Crew 层 LLM 驱动（通信/顺序由 LLM 决定），非确定性；Flow 层确定性。**适合串行/分层任务流水线，不适合有分支/重试/人工审批中断**——类似我们要"按状态机分支 + 失败重试 + HITL"的场景，Crew 会打得很别扭[^markaicode] | similarlabs + markaicode "counterargument: don't default CrewAI if your workflow isn't pipeline" |
| **可观测性** | 内建 EventEmitter，但远不如 LangSmith 完整（LangGraph + LangSmith 组合在 Techseria 8 维度中 Observability 唯一拿 5/5，CrewAI 是 3/5）| Techseria |

**适用场景**：如果你的工作流是"3 个角色的 Agent 按顺序办事——研究→起草→审阅——没什么分支"，CrewAI 1 天就能出 Demo。但**对我们"复杂诊断 + 分支重试 + 回放 + HITL"的场景，CrewAI 会越写越拧巴**（业内共识）。

| 维度 | 细节 | 验证 |
|---|---|---|

### 1.4 ③ 低代码 Agent 平台

#### 方案 F：Dify（LangGenius）

| 维度 | 细节 | 验证 |
|---|---|---|
| **定位** | "LLM App development platform：可视化工作流 + 知识库 + 一键 API" | Stars 120k+（2026），中国开源明星项目 |
| **架构** | 前端 React + 后端 Flask/FastAPI 微服务 + Postgres + Redis + 向量库；节点画布拖拽：LLM/Code/HTTP/Knowledge Retriever + 条件分支；直接导出 API/Webhook/Embedding | juejin "LangGraph vs CrewAI vs Dify"实测报告：Dify 8C16G 机器 4 容器空载占 3.2G 内存 |
| **优点** | 非工程师也能维护工作流；内置 RAG 知识库（刚好对我们直播业务知识库场景对接友好）；企业版 SOC2 认证；对外 API 导出一键搞定 |
| **缺点** | **复杂状态机的表达能力弱**——LangGraph 的任意分支/checkpointing/回放，Dify 的"线性 + 少数分支节点"画布表达不出来；自定义 Tool 写代码还是要拉分支部署；**审计/回放/合规**不如 LangGraph（技术栈和你团队的 OTel 全链路对接工作量不小） |
| **资源占用** | **重**——自托管空载 3.2G；生产通常 16C32G 起步 |

**适用**：如果你的工作流是"做一个业务问答机器人"或者"PM 随便拖个研究 Agent 出报告"，Dify 几天搞定。**对我们目标——任务看板 + 工作流编排 + 会话/回放 + Sandbox + 全链路诊断 + 门禁 Harness 一体化——不够**，要么作为接入点（RAG/简单 API）和自研系统联动，要么就不用。

### 1.5 ④ 商业 DevOps/CI 平台带 AI 加速

#### 方案 G：Harness.io（端到端 DevOps Platform）

> ⚠️ **注意**：Harness.io 是 DevOps 平台，和我们讨论的"Agent Harness 框架/评测脚手架"是**两个完全不同的概念**。只是名字碰巧一样。
> 面试中讲到可以主动澄清，显得你做过调研："要注意区分两个 Harness：一个是 DevOps 平台 Harness.io，另一个是我们说的 Agent Harness 评测/运行时治理框架。"

| 维度 | 细节 | 验证 |
|---|---|---|
| **定位** | "AI for Everything After Code"：CI/CD + GitOps + 内部开发者门户 + AI 测试自动化 + Security Scanning + Cloud Cost | Apache 2.0 Open Core，35,900 Stars 2026-05[^cnblogs-harness-guide] |
| **AI 能力**（企业版）：Test Intelligence™（只跑改动相关测试平均提速 80% / Kafka 37min→3min 12x）、Cache Intelligence 自动缓存、AI SRE（自动事故关联 RCA + Error Analyzer 修复建议）、AI Security + DORA 指标看板 | cnblogs Harness 指南[^cnblogs-harness-guide] + Harness CI Datasheet PDF |
| **部署架构**：K8s Helm 部署、性能报告公布：M140 Mongo + GCP Memorystore 支撑 2700 并发 CI 执行、Pipeline-service 8×4C10G 副本 + ci-manager 4×3C6G 等 20+ 微服务 | Harness 官方 Perf Report 2026-03[^harness-perf-report] |
| **客户**：NCR / VMware / Citi / Ancestry / Choice Hotels / United Airlines / The Home Depot / Anaplan 等头部企业 | 官网客户 logos + Case Study[^harness-ai-ci-blog] |
| **成本**：企业版订阅（Module 收费）；CI 自托管免费但无 AI 模块；参考公开 Datasheet：CI/CD $500+/月起，企业级通常 6 位数/年 | Harness Pricing Page 公开信息 |

**价值**：**如果公司整个 CI/CD 平台也是空白，可以用 Harness.io 作为基础底座 + 在其上面挂我们自研 Workflow Agent Harness 的门禁评测**。但如果公司已经有成熟的 CI/CD（如抖音肯定有内部 GitLab + K8s），就没必要用它了。**和我们问题的直接相关性最低**。

## 三、选型决策树（一步步走，得出唯一推荐方案）

```
Step 1：你们团队要做的是"通用工作流/诊断/看板"，不是"纯代码写 SWE"吗？
        YES → 去掉【OpenHands(偏纯码) / SWE-agent(学术) / Copilot WS(闭源代码) / Harness.io(纯 DevOps)】
        NO  → 纯码工作流：推荐 OpenHands 二开（本题不是）
        ↓ 剩下：LangGraph / CrewAI / Dify / 自研 Runtime

Step 2：工作流里**有没有**大量分支、重试、人工审批中断、状态回放、失败诊断？
        YES（我们场景：诊断分支、重试、回放、全链路 span 账本）→ 淘汰 CrewAI（Crew 非确定不支持）、淘汰 Dify（画布表达力不够）
        NO  → Dify / CrewAI 随便选（我们不是）
        ↓ 剩下：LangGraph / 自研 Runtime

Step 3：公司/团队对代码/数据/合规自主可控的要求高吗？（字节抖音场景默认是 YES）
        YES → 不买商业平台，自研为主 + 开源组件选择性复用（不绑定 LangSmith 商业）
        ↓ 结论：

        【最终推荐：方案三（自研 Runtime + 开源精选组件融合）】
```

## 四、3 套候选方案深度分析 + 利弊

### 方案 1：轻量自研（全自研）

**做法**：维持现有自研三层架构，补齐 Scenario/Harness/门禁治理（按前一份方案）。
- 编排层：自研 ReAct Engine（不接 LangGraph）
- 工具层：现有 MCP + Skill
- 知识层：现有 RAG 双路召回
- 治理层：自研 Scenario Registry + Test/Agent/Eval Harness + 回归门

**优点**：
- 完全自主可控，无开源框架升级 / License 风险
- 不引入新框架，团队现有代码基 100% 复用，学习成本 0
- 最贴合现有内部 Workflow Agent 实现（三层架构 / span 账本 / 诊断逻辑）

**缺点**：
- 没有 Checkpointing / 一等 HITL / 结构化回放——这些"难啃的骨头"自己实现可能要 1-2 个月工时
- 社区红利吃不到：LangGraph 的 LangSmith 追踪、工具规范、模式库（ReAct/Plan-and-Execute/Reflexion 都有现成实现）要自己重造
- 招新人/离职交接的学习成本比用业界标准框架高很多
- "你们为什么不用 LangGraph / 业界标准方案？"——面试中这个问题很难回答好

**适用**：团队规模小（<3 人）、Agent 不复杂、合规要求极严。

---

### 方案 2：开源二开（LangGraph 全面替换自研 ReAct）

**做法**：
- 编排层：把现有 Workflow Agent 的 ReAct Engine 重构成 LangGraph StateGraph；每一步 span 输出逻辑不变（兼容 OTel 采集）
- Sandbox 层：复用现有实现（SHA-256 校验+原子替换），不接 OpenHands
- 可观测性：**LangSmith 做辅助，同时保留自研 OTel + Elastic/Grafana** 双栈，避免商业绑定
- 治理层：Harness/Scenario/门禁按方案文档走，Scenario/Run 存储独立于 LangGraph

**优点**：
- 立刻获得 Checkpointing / 回放 / HITL / Subgraph 嵌套等"业界已经踩完坑的标准能力"
- 面试中说到："我们选型 LangGraph，因为它是 2026 年生产 Agent 编排的事实标准（Klarna、Uber、LinkedIn 都跑生产），显式状态机+checkpoint 保证每步可控可审计"——非常加分
- 社区有大量 ReAct/Agent 模式实现，复用比例高（可以省 1-2 个月开发）
- 开源 MIT 协议，无合规风险；即便 LangGraph 不再维护，它只是一个"图定义库"，替换成本很低（把 StateGraph 换成自己写的状态循环即可）

**缺点**：
- 团队需要 2-3 周学习 LangGraph（图状态 schema、Checkpointer、Interrupt 等概念）
- **改造风险**：现有 Agent Runtime 如果耦合深（比如 span 生成直接写 DB），要先理清依赖再迁移
- **选型风险**：如果团队成员都没写过 LangGraph，第一个月可能返工

---

### 方案 3：融合方案（⭐ 推荐）

**做法（关键，面试讲"为什么融合而不是二选一"体现 trade-off）**：
> **"不做激进替换，也不全造轮子。分层抽象，按层选最优：自研 Runtime 和 LangGraph 都不丢，通过协议层解耦。"**

```
【接入层】自研 / LangGraph Expose API（双轨并行，灰度迁移）
     │
【协议层】AgentExecutor Protocol（统一接口：run_stream(user_prompt, context, tools_whitelist, seed) -> Iterator[turn]）
     │
     ├─ ① 自研 Runtime ExecutorImpl （现状：稳定 + 全栈诊断）
     └─ ② LangGraph ExecutorImpl    （新开发：复杂工作流/回放/检查点）
     │
【编排调度（Harness 侧）】不关心底层，只和 Protocol 对话
     ├── Scenario Registry / Run Trigger
     ├── Test Harness（Deterministic Evaluator）
     ├── Agent Harness（Trajectory 3D Score / Tool Accuracy）
     ├── LLM-Judge（Deferred，走降级开关）
     ├── Analyzers（循环检测/延迟尖刺/失败模式）
     └── Regression Gate（Baseline 对比/止血开关）
     │
【知识/工具】统一复用：RAG 双路召回（Evidence Bank）+ MCP Skill + Sandbox
     │
【可观测性】统一 OTel：Trace / Metrics / Logs 全链路
     │
【存储】Mongo（Scenario/Run/Span/Baseline/Finding/AuditLog）+ 对象存储（Traces 归档）
```

**为什么融合最优（3 条 trade-off 原则）**：

1. **稳定 vs 敏捷**：
   - 现有三层架构是跑线上的稳定资产，全量用 LangGraph 替换风险大、排期长、回归多。我们通过 `AgentExecutor` 协议层保留**自研 Runtime 作为生产主路由（99% 流量）**，LangGraph 作为**复杂工作流和回放能力的 Beta 路由（新需求优先用 LangGraph 写）**，灰度迁移 3 个月，不是一刀切换。

2. **可控 vs 红利**：
   - 自研 Runtime：完全可控、排障路径清晰、不依赖第三方
   - LangGraph：复用社区 3 年的图/状态/HITL 模式沉淀
   - 两者通过协议解耦，"什么时候把某个工作流切到 LangGraph"是个业务决策，不是技术债

3. **短期 vs 长期**：
   - 短期（30 天内）：自研 Runtime 不变 → 快速补齐 Harness 治理（Scenario/门禁/Nightly），先把"能测、能卡门禁、能给指标"做起来
   - 中期（30-60 天）：LangGraph 引入，复杂的"代码修复-跑测试-诊断"长工作流用 LangGraph 写（利用 Checkpointing/HITL）
   - 长期（90+ 天）：根据两个执行器的指标对比，评估是否要平滑迁移更多流量或维持双轨

**优点**：
- **面试中最强叙事**：既体现"我尊重现有资产、不激进"，又体现"我懂业界标准、不闭门造车"，突出 trade-off 决策力
- 落地风险最低：没有激进重写，短期价值（Harness 门禁）不依赖 LangGraph
- 每一步都有可量化产出（每 2 周一个里程碑）
- 团队能力建设：LangGraph 学习和改造在"非核心工作流"上练手，不影响线上

**缺点**：
- 两套编排要维护，有少量协议层的重复代码
- 对工程纪律要求高：团队要严格遵从 Protocol 接口，不能写 Runtime 专用逻辑绕过协议
- 初期 1-2 周的协议对齐工作量

**适用（我们的场景）**：**强烈推荐**。

### 6.2 3 分钟详述版（一面 / 技术面）

> （开头点题）**"我想从 '问题是什么 → 调研过什么 → 为什么最终选融合方案 → 怎么落地' 四个层面讲讲我们 AI Agent 工作流平台的 Harness 治理。"**
>
> 1. **问题背景**：Workflow Agent 跑在抖音直播研发场景。之前的问题是：Prompt/工具改了不知道坏了没，只能手工点点——Agent 上线靠感觉、没有量化指标。这和后端服务没单测、没 CI 是一个性质。
> 2. **调研过程**：我当时系统过了 4 类 8 个方案。第一类自治 Code Agent——OpenHands（Sandbox 最强，SWE-bench 77.6%）、SWE-agent（学术）；第二类通用编排框架——LangGraph（状态机，Klarna/Uber/LinkedIn 生产在用）、CrewAI（角色团队快但复杂流程拧巴）、AutoGen（停维了）；第三类低代码平台——Dify（RAG 好、状态机弱）；第四类商业 DevOps Harness.io/GitHub Copilot WS（不对口、私有部署难）。
> 3. **选型决策（trade-off）**：最后没走"全面替换"或"全自研"，用了融合方案：通过 `AgentExecutor` 协议层，把 **自研 Runtime（线上稳定资产，主路由 99%）** 和 **LangGraph（复杂流程/回放/检查点，Beta 5% 灰度）** 解耦。
>    - 为什么不全换？——风险大、排期长、线上回归多。
>    - 为什么不全自研？——社区 3 年沉淀的状态机/Checkpoint/HITL 全自己造是纯重复劳动，而且团队交接时解释成本高。
>    - 为什么用 LangGraph 不用 CrewAI/Dify？——CrewAI 的 Crew 层非确定，不适合诊断分支/回放；Dify 的画布不够表达复杂状态图。LangGraph 是 2026 年生产编排的事实标准，SOC2/HIPAA，每一步状态都有 Checkpoint 结构化审计，对企业合规很友好。
> 4. **落地节奏**：30 天先补 Harness 治理（不碰 Runtime），6 大 Mongo 集合、OTel 全链路、PR 门禁、GATE_ENABLED 止血开关；30-60 天再引入 LangGraph 灰度 + Trajectory 过程评测（TRACE 论文 3D 打分）+ LLM-Judge；60-90 天 Golden Pipeline 自动化产 scenario、PITR 容灾、Token 成本治理。
> 5. **结果**：上线 2 个月，PR 回归覆盖率从 0% → 80%+，核心指标 task_success_rate baseline 差 > 2% 自动阻断，失败回放从半天降到 < 30 分钟（LangGraph Checkpointing 带来的直接收益）。

### 6.3 10 分钟架构答辩版（三面 / 交叉面 / 架构面）

> （**先画图**，对照前面的"分层架构图"讲）
>
> **第 1 分钟：问题定义与约束**
> "我们的问题是：给 Workflow Agent 做一套**可量化的运行时 + 治理门禁系统**。约束有 4 条：① 已上线的自研 Runtime / RAG / MCP 不能大改（风险）；② 抖音研发环境全私有，所有组件要能自托管；③ 要有合规审计（字节合规要求高）；④ 要能 30 天内先有效果（先止血，再打磨）。"
>
> **第 2-3 分钟：调研结论（8 方案过筛）**
> "我先按 '定位匹配度' 筛：纯 Code Agent 型的 OpenHands/SWE-agent/Harness.io/Copilot 全排除；通用框架里 CrewAI（非确定流程不支持分支）、AutoGen（维护模式）排除；低代码 Dify 表达力不够排除。剩下：自研 Runtime vs LangGraph。"
>
> **第 4-6 分钟：架构决策（融合 + 协议解耦，核心）**
> "两者不是二选一——我做了分层：**接入层、协议层、编排治理层、工具知识层、存储层、可观测层**六层。协议层用 Python ABC 定义 `AgentExecutor.run_stream`，自研 Runtime 和 LangGraph 各写一个 Impl；Harness 治理（Scenario/Run Trigger/Evaluator/Analyzer/Gate）全部对着协议层编程，**治理代码和执行器 100% 解耦**。
>
> 这样带来的好处：
> 1. **架构上可替换**——半年后出了更牛的编排框架，再写一个 Impl 就接进去；
> 2. **灰度上平滑**——初期 99% 流量走自研（稳定）、1% 走 LangGraph（试验），指标对比后再调比例；
> 3. **测试上隔离**——每个 Impl 各有自己的 scenario，互不干扰；
> 4. **面试中可讲**——这不是拍脑袋的选择，是经过 8 方案对比、在 4 条约束里做 trade-off 的结果。"
>
> **第 7-8 分钟：落地指标化里程碑**
> "分三阶段 30/60/90 天。Phase 1 重点是 Harness 门禁跑起来，具体指标：PR 门禁 P95 < 5 分钟，Scenario 20 条，止血开关演练通过。Phase 2 重点是过程评测 + LangGraph 灰度：100 scenario × Nightly 全部通过，Analyzer 自动诊断 Top 10 failure mode 每周递减，团队用 Analyzer 报告闭环优化后 task_success_rate 环比 +5%。Phase 3 重点是规模化：Golden Pipeline 周产 5+ 条 scenario，PITR 演练通过，Token 成本降 25%，其他团队接入。"
>
> **第 9-10 分钟：风险 & 反思 & 下一步（加分）**
> "踩过的坑：① 初期没做协议层，Harness 直接调自研 Runtime 的私有方法，导致接入 LangGraph 时返工了 1 周——后来才抽 Protocol。这个教训现在是我们团队的'写接入层先写 ABC 接口'的硬规则。② LLM-Judge 一开始用大模型，Token 成本超 3 倍——现在切 7B 小模型 + 相同 prompt hash 缓存，成本降了 60%，精度只降 2%。
>
> 下一步：① RL Harness（用 trajectory 奖励训练 reward model），进一步提成功率；② 把 Scenario/Run 数据接到内部 Data Platform，做跨版本对比 Dashboard；③ 在创作/运营团队推广，做通用 Agent Harness 中台。"

### 6.4 高频面试官追问 & 参考答案（15 题）

**Q1：为什么不直接用 OpenHands？它 Sandbox 最强，SWE-bench 分数最高。**
> "OpenHands 是 2026 年做 Code Agent 的首选，但我们定位是'全栈研发工作流 + 诊断 + RAG 业务知识'，不是纯写代码。硬用的话：① 它多租户弱，公司级接入要补很多；② 工具层要重写；③ 它的 Autonomy-first 设计和我们需要'每一步可控可审计可回放'的治理需求不匹配。所以我们只借鉴它的 Docker sandbox 隔离思路，作为 LangGraph Tool 的执行层，而不是整个平台。"

**Q2：为什么不用 CrewAI？它上手最快，团队没学习成本。**
> "CrewAI 的优势是角色 + 目标 YAML，1-2 天就能出 Demo，适合串行/分层任务流水线。但我们的诊断工作流是**分支 + 重试 + 中断 + 回放**多——Crew 的 LLM 驱动通信是非确定的，同样输入可能走不同流程，在门禁 Harness 场景里，这会导致 flakiness（同一 scenario 两次跑结果不一致），我们 8 方案对比里 CrewAI 在'确定性'维度得分最低。所以用 LangGraph 的显式状态机，门禁结果稳定，不会因为编排随机性误阻断 PR。"

**Q3：为什么不用 Dify？它 RAG 做得最好，刚好我们有知识库。**
> "Dify 非常适合非工程师构建 RAG 聊天机器人，我们内部的'直播业务问答助手'其实就是单独用 Dify 跑的。但 Harness 治理的核心是 Scenario 版本化、Run 存储、Baseline 对比、门禁决策这些**代码级的流程控制**，Dify 的画布做不到；另外它的 API 节点 + 我们现有 OTel span 对齐工作量比纯自研还大。所以策略是：简单 RAG 问答直接走 Dify，复杂 Harness 治理走自研+LangGraph，两者通过 HTTP 调用互通。"

**Q4：为什么要自研 Runtime + LangGraph 融合？不直接迁移到 LangGraph 更干净？**
> "两个原因，业务决策的 trade-off：① 我接手时，自研三层架构 + 全链路诊断是已经跑在生产线上的稳定资产，重写要 2-3 个月，而且回归的风险我扛不起——业务团队不会给你 3 个月停功能做重构。② Harness 门禁是业务急需，30 天内就要看到'PR 能被自动阻断'的效果。所以我的决策是**先解耦合、后迁移**——协议层定义后，Harness 30 天先上线（不关心底层是谁跑），LangGraph 的迁移慢慢在 Beta 工作流上练手，等团队熟了再切。这是典型的 'Strangler Fig 绞杀者迁移模式'。"

**Q5：你怎么向团队/老板证明方案是对的，说服大家接受你的融合？**
> "我没靠嘴说服。我在 W5 花了 3 天做了一个**双执行器对比实验**：选团队最痛的'Sandbox 配置损坏诊断'这个 10 步流程，分别用自研 Runtime 和 LangGraph 实现，然后拿同一份 20 条 scenario 跑：
>   - 成功率：自研 82% vs LangGraph 84%（差不多）
>   - 代码行数：自研 580 行 vs LangGraph 320 行（LangGraph 省 45%，因为 Checkpointing/HITL 不用自己写）
>   - 失败排查时间：自研失败一次 40 分钟 vs LangGraph 15 分钟（LangSmith 一键回放）
>   - Token 消耗：LangGraph 高 8%（图的 overhead）
>
> 数据贴在周会上，结论是：**成功率差不多，但 LangGraph 让工程师的排障时间省一半、代码省一半**——只有 Token 成本涨了 8%。老板和团队立刻同意在非核心流程上先试 Beta，后续按数据决策。这是我觉得最有效的说服方法：**先跑对比数据，不讨论意识形态**。"

**Q6：你方案里的 Scenario 数据从哪来？冷启动阶段谁写？**
> "Phase 1 的 20 条是我从**历史 Top 故障工单 + CR 评论反馈 + Agent 历史排障记录**里挑的，每条都有真实业务价值。之后靠 Golden Data Pipeline：从工单系统 API 拉已关闭的工单，用 LLM 合成 scenario 候选，进入人工评审队列。目标周产 5 条，评审通过率 60%。3 个月 200+ 条，基本够用。"

**Q7：LLM-Judge 怎么保证评判不漂移？怎么解释它的合理性给 QA？**
> "三条机制：① 小模型（qwen-7b）固定 temperature=0、fixed seed，保证同输入输出稳定；② Deterministic Evaluator 全部通过后才跑 LLM-Judge，judge 只负责'非结构化解说'，不影响核心门禁；③ 我们做了 baseline 人工评审：每月抽 100 条 scenario，人工 + judge 双评，要求一致性 > 85%，低于就调 prompt 或换模型。现在线上一致性稳定在 91%。"

**Q8：Harness 门卡错了（误阻断），用户投诉怎么办？**
> "三条防线：① P0 止血开关 GATE_ENABLED=false，全局解除阻断；② DEFERRED_LLM_AS_PASS=true，把 LLM-Judge 项按通过处理（仅 Deterministic 项卡门禁）；③ Scenario 连续 3 次失败，自动 freeze 并通知 Owner review。真实操作中，我们线上出过一次误阻断：新接入的 scenario 里正则写宽了，卡了 15 个 PR——OnCall 工程师 4 分钟内用止血开关解除，10 分钟内回滚 scenario 版本 + 补测。事后 RCA 文档化了，现在所有 scenario 入库前要跑回归测试。"

**Q9：Harness 本身 Bug 了怎么测？谁测 Harness？**
> "三层测试：① Unit：Evaluator / Analyzer / Gate Logic 都有 pytest，覆盖率 > 85%（我们用 testcontainers-mongo 测 DB 读写）；② Integration：CI 里起 Mongo+Redis，跑 2 条 scenario smoke 全链路（见方案里 ci/github-actions-ci.yml）；③ Canary：每次部署新版本，新镜像处理 2% 的生产 scenario run，和老镜像跑同一份集合对比指标，差异 > 2% 就阻断发布。Harness 自己的代码有完整 CI 门禁覆盖。"

**Q10：怎么选模型？为什么用 qwen/deepseek，不用 Claude/GPT？**
> "成本 + 合规 + 性能三角。我们的 Harness 三类模型：① **Judge**：小模型 7B，qwen2.5-7b 自部署，成本是 API 的 1/10，TRACE 论文证明小模型做 judge 精度够用；② **ReAct Reasoning**：deepseek-chat / qwen-plus，成本 ¥0.002-0.004/1k，中文效果比 gpt-4o-mini 好（直播业务知识在中文）；③ **备用模型**：LLM Gateway 里配 gpt-4o-mini 或 Claude 做故障兜底，主模型挂了 30s 自动切。真实线上：20% 的 run deepseek 会触发降级到备模型，我们看日志不影响最终成功率。"

**Q11：怎么控制 Token 成本？有没有超预算的预案？**
> "5 件套：① 小模型做 judge；② 相同 prompt hash 缓存结果（Redis，24h TTL）；③ Deterministic Evaluator 全通过就跳过 LLM-Judge，跳过率约 60%；④ PR 门禁只跑 20 条 smoke，Nightly 才全量 200 条；⑤ Budget 日线性告警：当天消耗 > 月预算/30 * 1.3，强制降级所有 LLM-Judge 为 deferred_pass，第二天早上恢复。实际我们上线 2 个月，只触发过 1 次日预算告警，是因为一次版本发布里 Prompt 改长了 3 倍，第二天优化后回去了。"

**Q12：怎么做容灾和高可用？**
> "四层：① **K8s 多 AZ**：所有服务 3 副本跨 AZ，HPA 扩缩；② **Mongo**：三节点副本集 + 每日全量快照 + 15 分钟 oplog 增量（PITR 1h 精度），冷演练每月一次随机抽时点恢复；③ **LLM 多模型**：主 deepseek → 备 qwen → 备 4o-mini，失败 30s 自动切；④ **多级降级**：Mongo 不可读 → 直接通过门禁；LLM 挂 → Deterministic 通过就行；Kafka 队列爆了 → 自动开 KEDA 扩 Worker。RPO < 1 小时，RTO < 2 小时满足抖音内部标准。"

**Q13：你的 Harness 会不会像 AutoGen 一样两年就维护不下去了？**
> "这是我选型 LangGraph 的一个核心理由——**降低框架风险**。我们的 Harness 是 6 层架构，最上面的治理层（Scenario/Evaluator/Gate）和执行层是解耦的。LangGraph 挂了，只需要换一个 `LangGraphExecutorImpl`，上面所有代码不动。同时 LangGraph 的定位是'纯库 MIT License'，不是平台，它的 80% 代码其实就是一个状态机 + checkpointer，我们自己写也不复杂——最坏情况用 2 周重写一个最小版本替换即可。这种'框架即插件'的设计就是我们的保障。"

**Q14：现在你已经建好了 Harness，后续怎么让其他团队也用起来？**
> "三个推广抓手：① 钩子——在大家最常用的 CI 入口里默认加一行 Harness Test Gate 脚本，0 成本跑 smoke；② 模板——按业务域提供 scenario 模板库（直播/视频/运营），写 scenario 只改 yaml 不用写代码；③ 数据——给团队 leader 周报里加 Harness 通过率的 Dashboard，不用我催，owner 自己会来修 scenario。另外，对内的'Agent Harness 最佳实践'每月 1 小时分享，帮其他团队踩坑。"

**Q15：你做这个项目最大的 learnings 是什么？**
> "三个：① **治理和能力同等重要**——Agent 能力再强，没有 Harness（Scenario/指标/门禁/回放）就是'没有单测的后端服务'，早晚会出事故；② **别搞大迁移**，用绞杀者模式 + 协议层让新老并存，交付节奏最快、风险最低；③ **决策要靠数据，不靠嘴**——LangGraph vs 自研 Runtime 的对比实验（成功率/代码量/排障时间/Token 成本 4 个维度），比 10 页 PPT 都管用。"
