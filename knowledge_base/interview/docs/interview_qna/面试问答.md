## 一、鸿蒙端业务与技术

### 1. 抖音直播鸿蒙端从 0 到 1 的建设过程是怎样的？你具体负责哪些部分？
**背景**：鸿蒙端是新平台，需要在没有现成基建的情况下完成直播业务落地。
**参考要点**：
- 背景：鸿蒙生态崛起，直播需要适配 HarmonyOS，复用抖音直播业务能力。
- 架构：从 0 搭建 H5/Lynx 混合架构容器，分层设计——容器基础能力、直播回放容器、核心业务组件。
- 我负责：架构设计与容器能力搭建、LiveView 接入、实况窗/直播卡片/小窗等鸿蒙特色能力接入、开播与看播全链路开发（福袋热点、开播框架）。
- 成果：性能提升 40%+，降低业务迁移成本 50%+，支持业务快速上线。

### 2. LiveView 是什么？在鸿蒙直播中如何接入？
**参考要点**：
- LiveView 是鸿蒙提供的直播渲染组件，支持视频流在系统层面的高效渲染与悬浮显示。
- 接入需要处理 ArkUI 与 LiveView 的生命周期协同、Surface 创建/复用、与小窗/后台播流的联动。
- 难点：与 App 切后台/前台、路由跳转时 Surface 回收与重建的时机控制。

### 3. H5/Lynx Hybrid 混合架构是怎么落地的？为什么选这种方案？
**参考要点**：
- 纯原生开发成本高、迭代慢；纯 H5 性能不足（首屏、交互流畅度）。
- 方案：核心播放/交互用 Lynx（类 RN 的高性能动态化框架），业务活动/活动页用 H5，通过容器桥接 JS Bridge。
- 容器职责：路由分发、预加载、生命周期管理、Bridge 通信、降级。
- 成果：业务迁移成本降低 50%+，兼顾性能与动态化。

### 4. ArkTS/ArkUI 与 TS/React 有什么区别？开发中踩过什么坑？
**参考要点**：
- ArkUI 声明式 UI（@Component、@State、@Prop、@Link），状态驱动渲染；与 React 思想相似但语法和运行时不同。
- 区别：V1/V2 状态管理版本差异、无法直接用 npm 生态、装饰器编译期校验、不支持任意 TS 特性。
- 坑：状态更新粒度、@Observed 嵌套对象不响应、列表渲染 key 管理、内存泄漏（组件销毁未解绑监听）。

## 二、KMP 跨平台

### 5. 为什么选 KMP？它和 Flutter、RN 的区别是什么？
**参考要点**：
- KMP（Kotlin Multiplatform）共享业务逻辑，UI 各端原生实现，保留原生体验。
- 对比 Flutter：Flutter 自绘 UI，体积大、与系统组件割裂；KMP UI 原生，更适合多端原生一致性要求高的直播场景。
- 对比 RN：RN 用 JS 写 UI，跨三端时与鸿蒙适配成本高；KMP 逻辑层共享，UI 层各端原生，鸿蒙用 ArkUI 实现。
- 直播场景：播放器/小窗/直播卡片强依赖原生能力，KMP 共享数据层、策略层最合适。

### 6. KMP 跨语言通信性能怎么优化的？
**参考要点**：
- 问题：Kotlin 与 ArkTS/JS/原生 之间通过 expect/actual、序列化、FFI 等方式通信，高频调用有开销。
- 优化：
  - 减少跨语言调用次数：批量传输、合并请求。
  - 数据结构优化：用 ByteArray/Protobuf 代替 JSON，减少序列化开销。
  - 异步化：耗时逻辑放 Kotlin 侧协程，通过回调/Flow 返回。
- 成果：数据传输效率提升 30%+。

### 7. KMP 三端代码复用率怎么做到 70%+？
**参考要点**：
- 共享：网络层、数据模型、业务策略、工具类、日志埋点等纯逻辑层。
- 不共享：UI 层（ArkUI/SwiftUI/Compose）、平台 API 封装（用 expect/actual 隔离）。
- 通过模块拆分 + 接口抽象，让业务核心逻辑无平台依赖。

### 8. Banner 业务从原生迁移到 KMP 的过程？
**参考要点**：
- 抽象 Banner 数据协议与轮播策略为 KMP 模块；各端只实现 UI 渲染与曝光埋点。
- 验证：数据一致性、曝光/点击埋点对齐、性能基线对齐。

## 三、AI Agent / Workflow Agent

### 9. Workflow Agent 平台的三层架构（Web/Runtime/Sandbox）是怎么设计的？为什么要分层？
**参考要点**：
- Web 层：会话管理、UI 编排、Workflow 定义、资产配置。
- Runtime 层（Codex Runtime）：Agent 执行引擎，ReAct 循环、工具调度、上下文管理，独立进程隔离模型推理与业务服务。
- Sandbox 层：工具执行、代码运行的隔离环境，保障安全与可重复。
- 为什么分层：隔离模型执行与业务服务，降低耦合；Sandbox 隔离避免工具执行污染主进程；便于独立扩缩容与故障隔离。

### 10. ReAct 模式是什么？和 Function Calling、Plan-and-Execute 有什么区别？
**参考要点**：
- ReAct = Reasoning + Acting，模型输出思考过程 → 调用工具 → 观察结果 → 再思考，循环执行。
- 区别：
  - Function Calling：单轮调用工具，缺乏多步规划。
  - Plan-and-Execute：先规划完整计划再执行，刚性高、纠错难。
  - ReAct：边想边做，灵活纠错，适合研发场景的长链路任务。

### 11. 你负责的全链路诊断是怎么做的？
**参考要点**（这是简历重点）：
- 链路追踪：traceId（整条 Workflow）、spanId（单个工具调用/推理步骤）、agentRunId（单次 Agent 运行）三级 ID 串联。
- 证据采集：Runtime Trace + Workflow 阶段账本（每个阶段的输入/输出/耗时/状态），作为确定性证据。
- 异常归因：定位到具体 span——是模型推理问题（幻觉/拒绝）、工具执行失败（参数错误/超时）、还是 Sandbox 状态异常（配置残留/TOML 损坏）。
- 修复建议：基于异常类型给出修复方向（如重试、改写 Prompt、回滚配置）。

### 12. Sandbox 配置同步的 SHA-256 校验、原子替换、失败回滚是怎么回事？
**参考要点**：
- 问题：多轮会话配置残留导致 TOML 损坏，Sandbox 状态不一致。
- 方案：配置变更计算 SHA-256 摘要，原子替换（写临时文件→rename），失败自动回滚到上一版本。
- 价值：保证 Sandbox 配置一致性，避免脏状态导致 Agent 执行失败。

### 13. MCP 协议是什么？你们的 Skill/MCP 扩展体系怎么设计的？
**参考要点**：
- MCP（Model Context Protocol）：标准化的模型 ↔ 工具/资源协议，让 Agent 能力可插拔。
- 我们的设计：动态工具注册（运行时注册 Skill，无需重启）、资产解析与版本锁定、Sandbox 物化、MCP 初始化。
- 价值：Agent 能力按需扩展，业务方可以自助接入新工具。

### 14. 上下文管理怎么做的？长对话 Token 超限怎么处理？
**参考要点**：
- 策略：滑动窗口 + 摘要压缩；保留最近 N 轮原文，更早的压缩为摘要。
- 工具结果裁剪：长输出（命令日志、代码）截断/摘要后入上下文。
- 关键状态持久化：Turn 级状态存库，支持会话恢复与回放。

## 四、RAG 知识库

### 15. RAG 双路召回是什么？为什么不全用向量检索？
**参考要点**：
- 向量检索：语义相近，但专有名词、ID、缩写召回差。
- 关键词召回（BM25/ES）：精确匹配强，但语义泛化弱。
- 双路：两路各召回 TopK，融合重排（RRF 或 cross-encoder 重排），兼顾语义与精确匹配。

### 16. 知识入库流水线怎么设计的？四类数据源如何统一处理？
**参考要点**：
- 数据源：Confluence、飞书文档、工单、代码注释。
- 流程：拉取 → 清洗（去噪、去重）→ 切分（按标题/语义/长度）→ 打标签（业务域、文档类型）→ Embedding → 入库（向量库 + 关键词索引）。
- 增量更新：基于文档版本/时间戳的增量同步。

### 17. Query Rewrite 和业务同义词词典解决什么问题？
**参考要点**：
- Query Rewrite：用户提问口语化/模糊，改写为检索友好的查询（如补全实体、拆解多意图）。
- 同义词词典：业务黑话映射（如"开播挂了"→"开播失败/崩溃"），提升召回率。

### 18. RAG 如何减少大模型业务幻觉？
**参考要点**：
- 检索到的知识作为事实证据注入 Prompt，约束模型只基于知识回答。
- 引用溯源：回答标注知识来源，无匹配时拒答而非编造。
- 与 Agent 结合：知识库作为 MCP Skill，Agent 需要业务事实时主动检索。

## 五、React Native 工程化

### 19. RN 拆包是什么？为什么做？怎么做的？
**参考要点**：
- 背景：RN Bundle 体积大，首屏慢；多业务模块耦合，发版互相阻塞。
- 拆包：按业务模块拆分 JS Bundle，主包 + 业务子包，按需加载。
- 实现：Metro 多入口打包、原生侧 Bundle 管理器按路由预加载/懒加载。
- 成果：首屏提速、业务独立发版、降低回归风险。

### 20. H5 打包优化做了什么？构建效率提升 40%+ 怎么做到的？
**参考要点**：
- 缓存：Webpack 5 持久化缓存（filesystem cache）。
- 并行：thread-loader、Terser 多进程压缩。
- 按需：Tree Shaking、动态 import、分包（splitChunks）。
- 体积：依赖分析、去重、替换重依赖。
- 成果：构建效率提升 40%+。

### 21. 赤兔元框架要解决什么问题？
**参考要点**：
- 痛点：内部工具众多，各项目重复搭建，维护效率低。
- 方案：统一 RN + Web 双端工程化框架，脚手架 + 构建 + 发布 + 组件库一体化。
- 价值：统一规范，降低新项目启动成本，提升维护效率。
