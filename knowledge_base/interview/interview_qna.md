# 面试深挖 Q&A 复习稿

> 使用建议：不要逐字死背，重点记住每题的「主结论 + 2 个支撑点 + 风险边界」。

## 0. 开播链路整体架构怎么讲？

**Q：你说做过开播链路，整体架构是怎么设计的？**

**A：**

开播不是一个单点功能，而是一条强状态、多阶段、多业务并发的复杂链路。它横跨预览、开播中、关播三个阶段，涉及相机、推流、美颜贴纸、礼物、连麦、小游戏、公屏等多条业务线。如果每个能力都散落接入，后续会很难维护。

所以我会把开播链路讲成三层：

- **编排中枢层**：`BroadcastCoreController` 作为核心 owner，管理会话状态机，以及预览、开播、关播、推流等子控制器。跨组件能力通过 `LiveContext` 获取，避免层层传参。
- **生命周期任务层**：把跟随页面生命周期执行的逻辑抽象成可插拔 `Task`，按 scene / priority 分发，统一清理。新增能力只要注册 Task，不需要改核心控制器。
- **组件化布局层**：基于 Tetris 把功能拆成 `Element` 动态挂载，比如 Toolbar、公屏、礼物、连麦、小游戏等，业务能力通过 serviceManager 注入。

**一句话总结：**

开播链路的核心不是「堆功能」，而是把多阶段、多业务、多资源的复杂链路收敛成一套可编排、可插拔、可灰度回滚的框架。

## 0.1 开播里的 Task 和 Element 有什么区别？

**Q：开播链路里为什么同时有生命周期 Task 和 Tetris Element？它们分别解决什么问题？**

**A：**

`Task` 和 `Element` 解决的问题不一样。

`Task` 偏生命周期和业务流程，比如进页面初始化、前后台切换、页面销毁、开关播阶段切换时要执行的逻辑。它解决的是「什么时候做什么事」。

`Element` 偏 UI 和组件挂载，比如 Toolbar、公屏、礼物盘、连麦坑位、小游戏背景等。它解决的是「什么东西展示在哪里」。

这两层拆开之后，业务扩展会更清楚：如果是生命周期逻辑，就加 Task；如果是一个 UI 能力，就加 Element。这样不会把页面生命周期、业务流程和 UI 布局全部混在一个大组件里。

**关键词：** Task 管生命周期，Element 管 UI 挂载；流程和展示解耦。

## 0.2 开播链路怎么保证状态和资源稳定？

**Q：开播涉及相机、推流、贴纸、连麦等资源，怎么保证状态不乱、资源不泄漏？**

**A：**

我会从三个层面保证稳定性。

第一是状态机。开播链路用明确的阶段流转，比如 `launchPreview → launchLive → onLiveEnd`，每一步都做准入校验，避免重复启动、权限不满足、媒体房拦截等异常路径直接进入下一阶段。

第二是生命周期统一分发。生命周期相关逻辑通过 Task 管理，`onShow / onHide / onForeground / onBackground / onDestroy` 这些时机统一分发，退出时统一清理，减少资源漏释放。

第三是灰度和回滚。新能力会通过 setting 开关控制，线上如果遇到问题可以快速回滚，不需要发版。

另外，开播页有些场景会主动关闭组件复用，避免复用外层 context 和频繁挂卸导致状态污染。这个取舍是为了优先保证主播侧链路稳定。

**一句话总结：**

开播稳定性的关键是状态机控流程、生命周期 Task 控清理、setting 控风险。

## 1. 短触为什么需要任务队列？没有队列会发生什么？

**Q：短触框架里为什么要设计任务队列？直接更新列表不行吗？**

**A：**

不行。短触的来源有 API、WRDS 消息、JSB 三类，可能在很短时间内同时触发 add、delete、activate。如果直接并发改 UIState，会出现三个问题：顺序不稳定、入场动画互相打断、临态或增强短触状态被覆盖。

所以我在 `ShortTouchManager` 里用任务队列把短触处理串行化。这样每个图标的加载、入场动画、状态更新都按顺序执行，保证列表渲染稳定，避免并发竞态。

**关键词：** 多来源并发、动画顺序、UIState 一致性、串行化。

## 2. 临态和增强短触有什么区别？

**Q：短触里的临态和增强短触分别是什么？为什么要分两套机制？**

**A：**

临态是普通短触的临时展示形态，比如短时间放大、加宽、前置，用来提升某个入口的曝光，展示结束后会自动回到常态。

增强短触是更高优先级的特殊入口，通常用于强运营活动。它是从候选短触里通过 `priority + dynamicPriority` 选出唯一一个展示，优先级高于临态。增强短触出现时，会压制或打断当前临态，保证强入口的视觉优先级。

**一句话总结：**

临态是「临时强化普通入口」，增强短触是「全局唯一强入口」。

## 3. 短触为什么要统一 API / 消息 / JSB 三种来源？

**Q：API、WRDS 消息、JSB 来源差异很大，为什么要统一成一套短触模型？**

**A：**

因为它们只是来源不同，后续处理逻辑是一样的：都要经过权限校验、配置过滤、排序、动画、临态、增强短触、埋点和卸载。

如果每个来源各写一套处理逻辑，后续策略会重复实现，而且容易出现体验不一致。统一成 `ShortTouchArea` / `ShortTouchItem` 这类结构后，所有来源都进入同一条流水线，由 `CommonShortTouchManager → ShortTouchManager → ViewModel → UI` 统一处理。

**价值：** 降低接入成本、统一体验、减少重复逻辑。

## 4. Hybrid 为什么要在容器层注入 LiveContext，而不是 JSB 自己取？

**Q：为什么 `LiveContext` 要由 `WebcastBizContainer` 注入到 `extraContainerContext`，而不是每个 JSB 自己去拿？**

**A：**

核心是为了收口上下文来源，避免 JSB 各自找全局状态导致耦合和串房风险。

容器最清楚当前页面属于哪个直播间、哪个 containerId，所以在 `onShow` 时统一把当前 `LiveContext` 注入到 `componentDelegate.extraContainerContext['liveContext']`。之后所有 JSB 都从这个上下文里取房间能力，比如 `messageManager`。

这样有三个好处：

- JSB 不依赖全局单例，边界更清晰。
- 同一个容器内的 JSB 共享同一个房间上下文。
- 容器销毁时上下文和监听能一起释放，减少泄漏和串房。

## 5. Hybrid 的 globalProps 为什么还要用 LiveContext 二次校正？

**Q：既然已经有 `getLiveLynxProps` 生成通参，为什么还要用 `LiveContext` 校正 `room_id / anchor_id / sec_anchor_id`？**

**A：**

因为 Hybrid 卡片可能存在复用、异步加载、切房等场景，通参生成时机和容器真实绑定的房间上下文不一定完全一致。

`LiveContext` 是当前容器实际绑定的房间上下文，所以我在 `LiveGlobalPropsService` 里用它对 `room_id / anchor_id / sec_anchor_id` 做二次校正，确保前端拿到的房间和主播信息与宿主一致。

这能避免两个问题：

- 埋点归因错误。
- 前端请求或展示串房。

## 6. KMP 哪些逻辑适合下沉？哪些不适合？

**Q：KMP 跨端时，什么逻辑适合放 commonMain？什么不适合？**

**A：**

适合下沉的是平台无关、业务稳定、需要多端一致的逻辑，比如 ViewModel、状态机、数据模型、消息解析、埋点口径、配置读取、业务判断。

不适合下沉的是强平台相关能力，比如复杂动画、系统播放器能力、ArkUI/Compose/UIKit 细节、页面生命周期差异、平台 SDK 调用。

我的原则是：**业务逻辑下沉，平台能力分叉。**

这样既能减少重复开发，也不会为了跨端复用牺牲各端的原生体验和稳定性。

## 7. KMP 为什么用 rawPayload / Protobuf，而不是 JSON？

**Q：KMP 消息桥接为什么通过 `rawPayload` 传 Protobuf 字节流，而不是直接传 JSON？**

**A：**

因为直播消息源头本来就是 Protobuf。直接传 `rawPayload` 有三个优势：

- **避免字段丢失**：JSON 中间转换可能漏掉未知字段或特殊类型。
- **保证双端一致**：Android 和 HarmonyOS 都从同一份 Protobuf bytes 解码，解析口径一致。
- **减少转换成本**：避免 Proto → JSON → Model 的二次转换。

当然 raw bytes 调试不方便，所以我补了 `raw_payload_base64` 的 mock 通道，方便在测试时构造消息并验证 KMP 侧解码链路。

## 8. KMP 的 iOS 现在是什么状态？会不会过度包装？

**Q：你说“一键三端”，那 iOS 已经落地了吗？**

**A：**

没有，这点我会明确说明。当前实际落地验证的是 Android 和 HarmonyOS，iOS 目前是架构预留和 FFI 方案对齐，还没有业务接入上线。

我讲「一键三端」更多是指架构目标和长期范式：`commonMain` 一份业务逻辑，Android / HarmonyOS 已落地，iOS 在模型映射、FFI 数据同步、渲染分叉上做预留。实际成果我会按「两端落地 + iOS 预留」来表述，避免过度包装。

## 9. 小窗最难的生命周期问题是什么？

**Q：小窗 / 画中画最难处理的是什么？**

**A：**

最难的是直播生命周期、播放器生命周期和页面生命周期三者不完全一致。

用户可能退后台、打开其它页面、从小窗回直播间、切换全屏页、开关播、被拉黑、切音频/视频流。任何一个时机没处理好，都可能出现画面暂停、声音异常、多个播放器同时存在、回房间状态不一致、内存泄漏等问题。

我的处理思路是：

- 明确小窗状态机，区分站内小窗、站外画中画、后台播放。
- 对播放器做显式 pause / resume / stop / release。
- 回直播间时统一收敛全屏页和小窗状态。
- 对多实例和监听器做清理，避免重复回调和泄漏。

## 10. 回放容器如何保证前端状态、本地 KV、开播参数一致？

**Q：直播回放容器里，前端设置、本地缓存、开播参数怎么保证一致？**

**A：**

这条链路我按「入口 → 容器 → JSB → 本地状态 → 开播参数 → 房间状态」打通。

前端通过 `live.getReplaySetting` 读取当前回放状态，通过 `live.updateReplaySetting` 更新设置；端上把关键状态写入本地 Repo，比如 `live_gen_play_open`、`live_play_auto_publish`。开播时 `CommonRoomParamInterceptor` 再从本地状态中读取并写入 `gen_replay` 参数。

付费直播比较特殊，`gen_replay` 不能只看开播页设置，而是要由门票里的 `ticketGenReplay` 覆盖，保证付费回放口径正确。

**一句话总结：**

通过 JSB 和本地 KV 把前端设置沉淀下来，再在开播参数构造时统一消费，保证前端、端侧和服务端口径一致。
