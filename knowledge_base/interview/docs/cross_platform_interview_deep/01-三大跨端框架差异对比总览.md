# React Native / Lynx / KMP 横向对比

## 1. 总览表

| 维度 | React Native | Lynx | KMP |
|---|---|---|---|
| 核心定位 | JS 驱动 Native UI 的跨端框架 | 高性能动态化页面 / 卡片容器 | Kotlin 业务逻辑跨端复用，也可共享部分 Compose UI |
| 主要复用 | UI 结构 + JS 业务逻辑 | 前端页面 / 活动逻辑 / 动态 UI | Model / ViewModel / State / Action / Service / 部分 Compose 组件 |
| 最终渲染 | Android View / iOS UIView | Lynx 引擎布局 + 各端渲染后端 | 原生 UI 渲染，或 KMP Compose 由平台容器承载 |
| 通信方式 | Bridge / JSI / TurboModule / EventEmitter | JSB / 容器事件 / globalProps | expect-actual / wrapper / delegate / callback / bridge |
| 动态化能力 | JS bundle 可更新 | 强动态化，适合活动和运营卡片 | 弱动态化，更偏发版型共享逻辑 |
| 性能关注 | JS Thread、Bridge、列表、动画 | 首屏、容器创建、JSB、事件频率 | 跨端桥接、对象同步、Compose 重组、生命周期释放 |
| 适合场景 | App 页面跨端 | 活动页、运营卡片、直播动态卡片 | 业务逻辑、状态机、消息、埋点、多端一致 |
| 不适合场景 | 极端性能链路、强 Native 能力 | 强本地复杂页面、长期重状态页面 | 强平台 UI、播放器、系统能力硬统一 |

## 2. 渲染差异

先用一张表把三者渲染本质区分开：

| 方案 | 谁描述 UI | 中间树是什么 | 谁做布局 / diff | 最终谁绘制 |
|---|---|---|---|---|
| RN | JS React Component | React/Fiber + Shadow Tree | React Reconciler + Yoga/Fabric | Android View / iOS UIView |
| Lynx | Lynx Bundle / 前端模板 | Lynx Element Tree / Layout Tree | Lynx Runtime + Layout Engine | Lynx 各端 Renderer + 平台渲染系统 |
| KMP 逻辑共享 | KMP 只描述业务状态 | RenderState，不是 UI 树 | 各端 UI 框架自己处理 | Android Compose/View、ArkUI、SwiftUI/UIKit |
| KMP Compose | Kotlin `@Composable` | Compose Composition / Slot Table | Compose Runtime 重组 | Compose 平台宿主 + 各端渲染系统 |

最关键的区别：

```text
RN
  -> JS 描述 UI
  -> RN 映射成 Native View

Lynx
  -> 前端 bundle 描述动态页面
  -> Lynx 引擎生成节点树并布局
  -> Lynx Renderer 落到平台渲染

KMP 逻辑共享
  -> KMP 只输出状态
  -> 各端自己写 UI 并渲染

KMP Compose
  -> KMP 写 @Composable
  -> Compose Runtime 管组合和重组
  -> 平台容器接入 UI 树
```

### React Native

```text
JS Component
  -> React Reconciler
  -> Shadow Tree / Fabric
  -> Native UIManager / Mounting
  -> Android View / iOS UIView
```

RN 的重点是：**JS 写 UI，Native View 渲染**。

它不是 WebView。最终屏幕上还是 Android / iOS 原生组件。

更准确地说：

```text
React Element
  -> Shadow Node
  -> layout result
  -> create/update Native View
  -> Android/iOS 系统绘制
```

### Lynx

```text
Lynx Bundle
  -> Lynx Runtime
  -> UI Tree
  -> Layout Engine
  -> Native Renderer
  -> Android / iOS / HarmonyOS 渲染后端
```

Lynx 的重点是：**动态化页面 / 卡片，Lynx 引擎负责布局和渲染调度，端侧容器提供能力**。

更准确地说：

```text
Template / Bundle
  -> Element Tree
  -> Layout Tree
  -> Render commands / platform nodes
  -> 各端 Renderer 绘制
```

直播场景下更关心：

- globalProps。
- JSB。
- LiveContext。
- 生命周期。
- 容器销毁。

### KMP

```text
commonMain
  -> Model / State / ViewModel / @Composable
  -> 平台 wrapper / actual
  -> Android / HarmonyOS / iOS 平台容器
  -> 原生 UI 或 Compose 渲染
```

KMP 的重点是：**共享业务语义**。

它可以只输出状态，也可以共享 Compose 组件：

- 逻辑共享：各端原生 UI 自己画。
- Compose 共享 UI：各端用平台宿主容器承载。

更准确地说：

```text
逻辑共享：
KMP RenderState
  -> platform wrapper
  -> native UI state
  -> platform UI render

Compose 共享 UI：
KMP @Composable
  -> Compose Runtime
  -> platform host
  -> platform render
```

## 3. 通信差异

### RN 通信

```text
JS
  -> Bridge / JSI
  -> Native Module
  -> callback / Promise / event
```

核心风险：

- 高频通信。
- 序列化成本。
- JS Thread 忙。
- Native Module 粒度过细。

### Lynx 通信

```text
Lynx JS
  -> JSB
  -> 端侧容器
  -> 业务 service / LiveContext
  -> callback / event
```

核心风险：

- JSB 注册分散。
- 容器上下文不一致。
- 切房 / 复用导致串房。
- 生命周期监听泄漏。

### KMP 通信

```text
平台 UI
  -> wrapper / delegate
  -> KMP ViewModel action
  -> KMP state / effect
  -> 平台 UI / 平台能力执行
```

核心风险：

- expect / actual 不对齐。
- 平台对象生命周期不一致。
- 大对象跨端同步成本高。
- Compose 组件和平台 View 混合时释放不完整。

## 4. 面试里怎么选型

### 什么时候用 RN

适合：

- Android / iOS 页面级跨端。
- 普通业务页面。
- React 生态复用。
- UI 和逻辑都希望由 JS 统一。

不适合：

- 播放器主链路。
- 高实时消息场景。
- 强 Native 生命周期页面。

### 什么时候用 Lynx

适合：

- 活动页。
- 运营卡片。
- 直播间动态入口。
- 需要快速下发和灰度的前端页面。

不适合：

- 强本地长期状态页面。
- 复杂系统能力重依赖页面。
- 需要大量端侧资源管理的核心链路。

### 什么时候用 KMP

适合：

- 多端逻辑一致。
- 状态机复杂。
- Model / 消息 / 埋点需要统一。
- 端侧 UI 可以分开实现。
- 或者需要共享部分 Compose 组件。

不适合：

- 所有平台 UI 强行统一。
- 播放器、系统窗口、小窗等强平台能力。
- 平台差异大且复用收益低的场景。

## 5. 直播场景选型口径

直播里可以这样判断：

```text
动态页面 / 活动卡片
  -> Lynx

普通跨端 App 页面
  -> RN

业务逻辑 / 状态机 / 消息 / 埋点一致
  -> KMP

播放器 / 小窗 / 系统生命周期
  -> 原生

KMP 组件需要嵌平台 View
  -> Compose + AndroidView / ArkUIViewTopLayer / UIKitView
```

一句话：

> 页面动态化优先 Lynx，页面级跨端可以 RN，业务逻辑复用优先 KMP，强平台能力保留原生。直播场景性能和生命周期要求高，所以更常见的是 Lynx 承载动态卡片、KMP 统一业务状态、原生处理播放器和系统能力。

## 6. 常见追问

### Q：RN 和 Lynx 都能跨端 UI，区别是什么？

A：

RN 是 JS 驱动 Native UI，适合 App 页面级跨端；Lynx 更偏端内动态化页面和卡片，强调快速下发、容器能力和首屏性能。直播活动卡片、运营入口更适合 Lynx。

### Q：KMP 和 RN / Lynx 最大区别是什么？

A：

RN / Lynx 更偏 UI 或页面跨端，KMP 更偏业务逻辑跨端。KMP 不要求一套 UI 到处跑，而是把 Model、State、ViewModel、消息、埋点这些多端必须一致的部分下沉。

### Q：KMP Compose 组件最终怎么显示？

A：

Compose Runtime 执行 `@Composable`，平台宿主把结果接到 UI 树。Android 用 ComposeView 承载 Compose，用 AndroidView 嵌原生 View；HarmonyOS 用 ArkUIViewTopLayer / ArkUIComponentContent 承载 ArkTS 创建的 ComponentContent；iOS 用 ComposeUIViewController / UIView 或 UIKitView。

### Q：为什么直播里不全部用一种跨端方案？

A：

因为直播里不同问题的性质不同。动态活动页面要快速下发，用 Lynx；业务状态和消息口径要一致，用 KMP；播放器、小窗、系统能力强依赖平台，保留原生。统一技术栈不是目的，合适的边界才是关键。

## 7. 更细的选型矩阵

| 问题类型 | 更适合的方案 | 原因 | 风险点 |
|---|---|---|---|
| 普通双端业务页面 | RN | UI 和逻辑可用 JS 统一，生态成熟 | JS Thread、Bridge、首屏和 Native 能力 |
| 活动页 / 运营卡片 | Lynx | 动态下发强、端内容器能力强、首屏更可控 | 容器上下文、JSB 安全、生命周期 |
| 直播间动态入口 | Lynx + 原生容器 | 前端快速迭代，端侧注入 LiveContext | 切房串参、监听泄漏、白屏 |
| 多端业务状态机 | KMP | commonMain 统一状态、消息、埋点口径 | sourceSet 对齐、平台桥接 |
| 共享轻量组件 | KMP Compose | 组件结构可复用，各端容器承载 | Compose 重组和平台 View 生命周期 |
| 播放器 / 小窗 / PiP | 原生 | 强系统能力和平台生命周期 | 多端逻辑重复，需要抽公共语义 |
| Hybrid 容器能力 | Lynx / WebView + 原生 | 动态页面需要端侧服务能力 | JSB 权限、通参、容器复用 |
| 消息解析 / 埋点字段 | KMP | 多端一致性收益高 | rawPayload 解析、字段兼容 |

## 8. 成本模型对比

选型时不能只看“能不能跨端”，还要看成本来自哪里。

### RN 的成本

- JS Runtime 初始化。
- JS Thread 执行和 React render。
- Bridge / JSI 跨边界通信。
- Native Component 封装成本。
- 大列表和动画性能治理。
- bundle 版本和 Native Module 兼容。

### Lynx 的成本

- 容器创建和 bundle 加载。
- JSB 注册、权限和参数校验。
- globalProps 注入和更新。
- 页面 / 容器 / 房间生命周期对齐。
- 离线包和 fallback。
- 白屏、首屏、JS error 监控。

### KMP 的成本

- commonMain 边界设计。
- expect / actual 对齐。
- 平台 wrapper 维护。
- 类型、nullable、枚举、默认值同步。
- Compose 共享 UI 的平台容器适配。
- State / Effect 生命周期管理。

一句话：

> RN 的成本主要在 JS 与 Native 协同，Lynx 的成本主要在动态容器和端侧能力治理，KMP 的成本主要在跨端边界和平台桥接一致性。

## 9. 三者组合架构

直播里更现实的架构不是三选一，而是组合使用。

```text
Native Room
  -> Player / PiP / Lifecycle / MessagePlatform
  -> Lynx Container
       -> 动态活动卡片
       -> JSB 调直播能力
       -> globalProps / LiveContext
  -> KMP Business
       -> Model / State / Action
       -> Message parser
       -> Setting / Event params
       -> optional Compose UI
```

组合后的分工：

- 原生：管强平台能力和主链路稳定性。
- Lynx：管动态页面、活动卡片和前端快速迭代。
- KMP：管业务语义一致、状态机、消息解析和埋点。

这套口径适合解释复杂项目：

> 我不会把所有问题都塞进某个跨端框架，而是按问题性质拆边界。动态化交给 Lynx，一致性逻辑交给 KMP，平台强能力保留原生，容器层负责把它们串起来。

## 10. 常见误区

### 误区 1：RN / Lynx / KMP 都是跨端，所以可以互相替代

不准确。RN 更偏页面级跨端，Lynx 更偏动态化卡片和容器，KMP 更偏业务逻辑共享。

### 误区 2：KMP 不渲染 UI

不准确。KMP 可以只共享逻辑，也可以用 Compose Multiplatform 共享部分 UI。区别在于最终仍要通过 AndroidView、ArkUIViewTopLayer、UIKitView 等平台容器落地。

### 误区 3：Lynx 比 WebView 快，所以所有 H5 都该换 Lynx

不准确。Lynx 适合端内动态化和强端能力卡片；标准网页、外部内容、复杂 Web SDK 依赖仍可能更适合 WebView。

### 误区 4：RN 新架构有 JSI，所以通信没有成本

不准确。JSI 减少传统 Bridge 成本，但跨 runtime、跨线程、跨平台能力仍然有成本。高频事件仍要聚合和批量化。

### 误区 5：跨端就是为了少写代码

不完整。少写代码只是结果之一，更重要的是减少多端语义漂移，让状态机、消息、埋点、配置默认值在多端一致。

## 11. 面试延伸问答

### Q：如果一个直播卡片既要动态下发，又要复用多端状态机，怎么设计？

A：

我会把 UI 动态化放在 Lynx，业务状态和数据决策放在 KMP。端侧容器负责创建 Lynx 卡片并注入 LiveContext；KMP 输出状态、schema、埋点参数或消息解析结果；Lynx 通过 JSB 向端侧发 action，端侧再转给 KMP 或原生服务处理。这样前端能快速迭代，状态和埋点又不会多端漂移。

### Q：RN 和 Lynx 都是 JS 驱动，为什么直播活动卡片更偏 Lynx？

A：

RN 更适合 App 页面级跨端，页面生命周期和 Native 集成相对重；Lynx 更偏端内动态化容器，bundle、JSB、globalProps、离线包和首屏性能都更适合活动卡片。直播活动入口通常生命周期短、迭代快、依赖房间上下文，所以 Lynx 更合适。

### Q：KMP Compose 和 RN / Lynx 的 UI 跨端有什么不同？

A：

RN / Lynx 是 JS 或前端 bundle 驱动 UI，再映射到端侧渲染；KMP Compose 是 Kotlin Compose Runtime 驱动组件组合，最终通过平台容器接入 Android / HarmonyOS / iOS UI 树。KMP Compose 更适合和 Kotlin 业务状态结合，但动态下发能力弱于 Lynx。

### Q：跨端方案最重要的工程能力是什么？

A：

不是会用某个框架，而是会划边界。哪些放动态化，哪些放 shared logic，哪些必须原生，哪些能力通过 bridge 暴露。边界划错，跨端会变成性能问题、生命周期问题和多端兼容问题的集合。
